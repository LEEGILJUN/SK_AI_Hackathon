> 예: "이거 형식 맞는지 봐줘" (+ 작성한 yaml 붙여넣기)

GitHub이 자동으로 형식을 검사해 커밋 옆에 ✅ 또는 ❌ 를 표시합니다.

====================== 여기부터 복사 ======================

당신은 제조 AI 외관검사 시스템의 시연 시나리오를 작성하는 일을 돕습니다.
저는 배터리 도메인과 머신비전을 아는 품질 담당자이고, 무엇이 옳은 판정인지를
정의하는 역할입니다.

## 배경

이미 배포된 AI 외관검사 모델(PatchCore)이 불량을 못 잡았을 때, 에이전트가
원인을 진단합니다. 저는 그 진단을 채점할 시나리오 20건과 정답을 만듭니다.

PatchCore는 정상 이미지의 패치를 메모리 뱅크에 담아두고, 검사 이미지가 그
뱅크에서 얼마나 멀리 떨어져 있는지(이상 점수)로 판정합니다. 그래서 못 잡은
경우 그 이미지가 뱅크의 **어느 정상 패치와 가까웠는지**를 되짚을 수 있습니다.

데이터는 VisA 공개 데이터셋(capsules, pcb1, macaroni1 등 객체 12종,
1500x1000 해상도, 결함 크기 약 40x40px)을 가상 공장으로 재구성해 씁니다.
사내 데이터는 일절 쓰지 않으므로 실제 공정 조건이나 장비 공급사명은
절대 넣지 마세요.

## 미검출 원인 6종

| 원인 코드 | 한국어 | 어떤 상황인가 | 뱅크 재구성 |
|---|---|---|---|
| `threshold` | 임계값 문제 | 이상 점수는 높은데 임계값 아래에 있음 | **false** |
| `bank_contamination` | 뱅크 오염 | 최근접 정상 패치가 알고 보니 결함이었음 | **true** |
| `coverage_gap` | 커버리지 부족 | 현재 조건의 정상 패치가 뱅크에 없음 | **true** |
| `normal_overlap` | 정상 분포 중첩 | 최근접 패치가 진짜 정상품인데 형상이 유사 | **false** |
| `equipment_optics` | 설비·광학 | 화질 지표가 기준 분포를 이탈 | **false** |
| `criteria` | 기준 문제 | 검출은 했으나 판정 기준상 양품으로 분류 | **false** |

**여섯 중 넷은 뱅크를 다시 만드는 것이 답이 아닙니다.** 이 서비스의 가치는
불필요한 재학습을 막는 데 있고, 진단 성능의 시험대는 "재학습을 해야 할 때
하는가"가 아니라 **"하지 말아야 할 때 멈추는가"** 입니다.

`requires_bank_rebuild` 는 원인이 정해지면 위 표대로 따라옵니다.
절대 임의로 정하지 마세요.

## 판별 항목 7가지

진단 에이전트는 이 7가지를 조합해 원인을 가릅니다. 정답(`evidence`)에
각 항목의 값을 적어야 합니다.

| 번호 | 필드 이름 | 값 | 무엇을 보는가 |
|---|---|---|---|
| 1 | `defect_visible` | true / false | 결함이 이미지에 실제로 보이는가 |
| 2 | `quality_within_baseline` | true / false | 화질 지표가 기준 분포 **안**인가 |
| 3 | `score_vs_threshold` | `above` / `near` / `below` | 이상 점수가 임계값 대비 어디인가 |
| 3-1 | `score_ratio` | 숫자 (점수÷임계값) | 예: 0.92 |
| 4 | `nearest_patch_ref` | `{source_image, patch_index}` | 최근접 정상 패치의 출처 |
| 5 | `nearest_patch_is_defect` | true / false | **그 패치가 결함인가 진짜 정상품인가** |
| 6 | `coverage_present` | true / false | 현재 조건의 정상 패치가 뱅크에 있는가 |
| 7 | `criteria_verdict` | `defect` / `pass` / `review` | 판정 기준상 불량이 맞는가 |

**5번이 가장 중요합니다.** 4번으로 최근접 패치를 찾아도, 그것이 잘못 들어간
결함인지 진짜 정상품인지를 구분해야 원인이 갈립니다.
결함이면 뱅크 오염, 진짜 정상품이면 정상 분포 중첩이며 **조치가 정반대**입니다.

원인별로 반드시 맞아야 하는 값:

- `bank_contamination` → `nearest_patch_is_defect: true`
- `normal_overlap` → `nearest_patch_is_defect: false`
- `equipment_optics` → `quality_within_baseline: false`
- `coverage_gap` → `coverage_present: false`
- `criteria` → `score_vs_threshold: above` 이면서 `criteria_verdict: pass`

## 인테이크 판정

원인 6종과 **별개 축**입니다. 진단 이전 단계입니다.

- `proceed` — 정보가 충분하다. 진단으로 넘긴다
- `need_more_info` — 라인이나 이미지가 없다. 되묻는다 (이때 `cause` 는 null)
- `duplicate` — 이미 해결된 사례다 (이때 `duplicate_of` 필요, `cause` 는 null)

## 출력 형식

아래 형식을 정확히 지켜 주세요. 필드 이름이 코드에서 그대로 읽힙니다.

```yaml
  - id: SC-XX-001                 # SC-{원인약어}-{번호}. BC/NO/TH/CV/EQ/CR
    title: 한 줄 요약
    cause_group: bank_contamination
    priority: mvp                 # mvp | extended

    target:
      line: line_02
      object: capsules            # VisA 객체명
      bank_version: v3
      lot_ids: [LOT-20260605-014]
      date_range: [2026-06-05, 2026-06-07]

    input:
      issue_text: "현장 사람이 실제로 칠 법한 문장"
      attachments:
        - line_02/2026-06-05/LOT-20260605-014/img_0142.png
      reporter_role: 공정엔지니어
      submitted_at: 2026-06-07T22:10:00

    injection:                    # 이 상황을 데이터에서 어떻게 만드는가
      method: bank_contamination  # bank_contamination | threshold_shift |
                                  # coverage_exclude | overlap_select |
                                  # image_degrade | criteria_change | none
      seed: 20260605
      params:
        contaminated_images: [capsules/Data/Images/Anomaly/000.JPG]
        contaminated_count: 3

    ground_truth:
      intake_verdict: proceed
      cause: bank_contamination
      requires_bank_rebuild: true     # 원인에서 따라오는 값
      duplicate_of: null
      evidence:
        defect_visible: true
        quality_within_baseline: true
        score_vs_threshold: below
        score_ratio: 0.92
        nearest_patch_ref:
          source_image: capsules/Data/Images/Anomaly/002.JPG
          patch_index: null
        nearest_patch_is_defect: true
        coverage_present: true
        criteria_verdict: defect
      expected_actions: [remove_contaminated_samples, rebuild_bank, shadow_compare]
      forbidden_actions: [lower_threshold]

    scoring:
      weight: 1.0
      cause_match: exact
      grade_evidence: true
      evidence_required: [nearest_patch_is_defect, defect_visible]
      tolerance: {score_ratio: 0.10}
      notes: >
        이 케이스에서 무엇을 맞혀야 정답인지
```

## 작성할 때 지켜 주세요

1. **`issue_text` 는 사람이 실제로 칠 법한 문장으로.** 이 문장이 언어 모델에
   그대로 들어갑니다. 전부 정제된 문장이면 현장에서 오는 거친 입력을 처리하지
   못하는 채로 시연에 갑니다. **20건 중 4~5건은 일부러 불완전하게** 써 주세요
   — 라인 번호를 빼거나, 결함 이름을 다르게 부르거나, "요즘 자꾸 빠지는거
   같은데 확인좀" 같은 야간 메모처럼.

2. **정답을 먼저 확정하고 데이터를 만듭니다.** 순서가 뒤집히면 채점이
   무의미해집니다.

3. **`requires_bank_rebuild` 를 손으로 정하지 마세요.** 원인 표를 그대로
   따르세요. 이 값이 "재구성이 답이 아닌 케이스 전건 차단"이라는 정량 목표의
   채점 기준입니다.

4. **재구성이 답이 아닌 원인에서 `expected_actions` 에 `rebuild_bank` 를
   넣지 마세요.**

5. 사내 정보(실제 공정 조건, 장비 공급사, 생산 거점, 사내 결함 정의)는
   어디에도 넣지 마세요.

## 지어내지 말고 저에게 물어봐 주세요

저는 배터리 도메인과 머신비전을 아는 사람이고, 현장에서 실제로 무엇이
문제가 되는지 알고 있습니다. **당신이 그럴듯한 시나리오를 지어내면 시연이
교과서처럼 보입니다.** 심사위원도 현장을 아는 사람일 가능성이 높습니다.

시나리오를 쓰기 전에 저에게 물어봐 주세요. 예를 들면 이런 것들입니다.

- 실제로 미검출이 났을 때 현장에서 제일 먼저 의심하는 것은 무엇입니까?
- "이건 아무리 데이터를 넣어도 안 잡히더라" 했던 결함 유형이 있습니까?
- 학습 데이터에 불량이 섞여 들어간 적이 있습니까? 어떻게 알아챘습니까?
- 검사기가 잡았는데 기준 때문에 양품으로 흘러간 일이 있습니까?
- 어느 시점부터 갑자기 성능이 떨어졌던 경험이 있습니까? 원인이 뭐였습니까?
- 신규 로트나 자재 배치가 바뀌었을 때 검출률이 흔들린 적이 있습니까?
- 접수자가 이슈를 올릴 때 보통 어떤 정보를 빠뜨립니까?

제 답을 듣고 그것을 시나리오로 옮겨 주세요. 제가 겪은 일이 재료입니다.
한 번에 다 묻지 말고 두세 개씩 물어봐 주세요.

**특히 마지막 질문이 중요합니다.** 접수 문장이 현실적이어야 인테이크
에이전트가 제대로 검증됩니다. 실제로 현장에서 올라오는 문장이 어떤지
알려드리면 그대로 써 주세요.

## 붙여넣은 뒤에 할 일

1. 나온 YAML을 `data/scenarios.yaml` 의 `scenarios:` 아래에 붙여넣습니다
   (GitHub 웹에서 파일 열고 연필 아이콘 ✏️ → 붙여넣기 → `Commit changes`)
2. 커밋하면 자동 검사가 돕니다. 1~2분 뒤 커밋 옆에 ✅ 또는 ❌ 가 뜹니다
3. ❌ 면 눌러서 메시지를 읽고, 그 메시지를 다시 웹 클로드에 붙여넣어
   고쳐 달라고 하시면 됩니다

들여쓰기가 어긋나면 검사가 "YAML 형식이 깨졌습니다"라고 알려줍니다.
이 경우가 제일 흔하니, 붙여넣을 때 앞쪽 공백 개수를 기존 항목과 맞춰 주세요.
