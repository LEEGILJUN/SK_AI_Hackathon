
# 웹 클로드에 붙여넣을 자료 — 가상 메일 작성용 (장영진)

이슈가 현장에서 올라오는 실제 경로는 메일입니다. `docs/기획서.md` 의 As-Is
설명도 "담당자에게 메일이나 메신저로 전달되고" 로 시작합니다. 접수 입력을
메일로 만들면 인테이크 에이전트가 훨씬 현실적인 조건에서 검증됩니다.

**먼저 [`examples/웹클로드에_붙여넣기_시나리오.md`](웹클로드에_붙여넣기_시나리오.md)
를 읽으세요.** 이 문서는 그 작업의 `input` 부분만 다룹니다.

---

## 1. 메일은 어디에 들어가는가

인테이크 에이전트는 문자열 하나를 받습니다 (`agents/intake.py` 의
`receive(text=...)`). 그래서 **메일 본문을 `issue_text` 에 그대로 넣으면
코드를 한 줄도 고치지 않고 동작합니다.**

그것만으로 충분한지가 지금 정할 문제입니다.

| 방식 | 하는 일 | 코드 변경 |
|---|---|---|
| A. 본문만 | 메일에서 사람이 쓴 문장만 뽑아 `issue_text` 에 | 없음 |
| **B. 메일 통째로 (권장)** | 헤더·인용·서명까지 원문 그대로 `issue_text` 에 넣고, 구조화된 값은 `input.email` 에 따로 | 없음 |

**B 를 권합니다.** `input.email` 은 **선택 필드**라 기존 코드가 무시하므로
지금 넣어도 깨지는 곳이 없고, 나중에 메일 파서를 붙일 때 그대로 쓰입니다.
A 로 시작하면 나중에 20건을 다시 손봐야 합니다.

```yaml
    input:
      # 인테이크에 실제로 들어가는 값. 메일 원문 그대로.
      issue_text: |
        보낸사람: 김공정 <gongjeong.kim@example.com>
        받는사람: 검사기술팀 <vision-ops@example.com>
        제목: Re: [2라인] 캡슐 표면 찍힘 미검 건
        보낸시각: 2026-06-07 22:10

        검사기술팀 담당자님,

        지난주부터 말씀드린 건인데 아직도 계속 빠집니다.
        육안으로는 명확한데 검사에서 양품으로 나옵니다.
        이미지 2장 첨부합니다. 확인 부탁드립니다.

        > 2026-06-05 김공정 wrote:
        > 2라인 캡슐 쪽에 찍힘이 몇 건 보입니다. 일단 공유드립니다.

        --
        김공정 책임
        공정기술 / 가상제조 주식회사

      # 위 원문에서 사람이 읽어낸 값. 채점과 대조에 씁니다.
      email:
        from_role: 공정엔지니어          # 실명이 아니라 역할
        thread_depth: 2                 # 주고받은 횟수. 1이면 첫 메일
        has_quoted_history: true        # 인용된 이전 대화가 있는가
        subject_matches_body: true      # 제목과 본문이 같은 건을 말하는가

      attachments:
        - line_02/2026-06-05/LOT-20260605-014/img_0142.png
        - line_02/2026-06-06/LOT-20260605-014/img_0311.png
      reporter_role: 공정엔지니어
      submitted_at: 2026-06-07T22:10:00
```

`reporter_role` 은 기존 필드이니 그대로 두고, `email.from_role` 과 같은 값을
씁니다. 중복처럼 보이지만 하나는 시나리오 메타이고 하나는 메일 파싱 정답입니다.

## 2. 메일이 시험하는 것

메일을 쓰는 이유는 분위기가 아닙니다. 인테이크의 판단 두 가지를 시험하기
때문입니다.

**정보 충분성** — 메일은 정제된 양식보다 훨씬 잘 빠집니다. 라인 번호를
제목에만 쓰고 본문엔 안 쓰거나, "그 건" 이라고만 하거나, 첨부를 깜빡합니다.
`agents/intake.py` 는 라인과 품목이 없으면 되묻고, 첨부가 없으면 이미지를
요청합니다. 그게 실제로 걸리는지 봐야 합니다.

**중복 차단** — 이게 메일의 진짜 값어치입니다. 전달(Fwd) 스레드에 **이미
해결된 과거 건이 인용돼 있는** 메일을 만들면, 인테이크가 중복을 잡아내는지
자연스럽게 시험됩니다. 양식 입력으로는 만들기 어려운 조건입니다.

그리고 메일에만 있는 잡음이 있습니다. 서명 블록, 인용 기호(`>`), 자동 문구,
제목과 본문 불일치, **한 메일에 두 가지 건이 섞여 있는 경우**. 언어 모델이
여기서 엉뚱한 값을 뽑으면 잘못된 라인의 뱅크를 건드리게 됩니다.

## 3. 가장 조심할 것 — 사내 정보

**시나리오 20건 중 메일이 사내 정보 유출 위험이 제일 큽니다.** 실제 이름,
사번, 사내 메일 도메인, 조직명, 결재선, 시스템 이름이 자연스럽게 딸려 오기
때문입니다. 실제 메일을 참고해 쓰다 보면 특히 그렇습니다.

규칙을 고정합니다.

| 항목 | 쓸 것 | 쓰지 말 것 |
|---|---|---|
| 메일 도메인 | `@example.com` (표준 예약 도메인) | 실제 사내·거래처 도메인 |
| 사람 이름 | `김공정`, `이품질` 같은 역할 조합 가상명 | 실존 인물 이름, 사번 |
| 회사·조직 | `가상제조 주식회사`, `검사기술팀` | 실제 사명, 실제 팀명, 생산 거점 |
| 라인·품목 | `line_02`, `capsules` (기존 표기 그대로) | 실제 라인 번호·설비 ID |
| 결함 이름 | 일반어 (`찍힘`, `눌림`, `이물`) | 사내 결함 코드 체계 |
| 장비 | 언급하지 않음 | 장비 공급사명, 모델명 |

**실제 받은 메일을 복사해서 이름만 바꾸는 방식은 쓰지 마세요.** 문장 구조와
표현에 사내 맥락이 남습니다. 상황만 참고하고 새로 쓰세요.

## 4. 20건을 어떻게 배분하는가

시나리오 20건에 1:1로 붙이되, 메일 성격을 흩어 놓습니다.

| 성격 | 건수 | 무엇을 보는가 |
|---|---|---|
| 잘 쓴 첫 메일 | 6 | 정상 경로. `proceed` 가 나와야 함 |
| 정보가 빠진 메일 | 4 | 라인·품목·첨부 중 하나가 없음 → `need_more_info` |
| 전달·인용 스레드 | 4 | 인용문에서 엉뚱한 값을 뽑지 않는가 |
| 해결된 건이 인용된 전달 | 2 | → `duplicate` 로 끊기는가 |
| 두 건이 섞인 메일 | 2 | 하나만 골라 처리하는가, 되묻는가 |
| 야간 급한 메모 | 2 | 문장이 거칠어도 처리되는가 |

**전부 잘 쓴 메일이면 인테이크는 검증되지 않습니다.** 절반 가까이는 일부러
불완전해야 합니다.

====================== 여기부터 복사 ======================

당신은 제조 AI 외관검사 시스템의 시연용 **가상 이슈 접수 메일**을 쓰는 일을
돕습니다. 저는 배터리 도메인과 머신비전을 아는 품질 담당자입니다.

## 배경

이미 배포된 AI 외관검사 모델이 불량을 못 잡았을 때, 에이전트가 원인을
진단합니다. 그 시작점이 현장에서 올라오는 메일입니다. 이 메일이 언어 모델에
그대로 입력되어 라인·품목·결함유형·기간이 추출됩니다.

접수 단계(인테이크)는 두 가지를 판단합니다.

- **정보가 충분한가** — 라인과 품목이 없거나 이미지 첨부가 없으면 되묻습니다
- **이미 해결된 사례인가** — 같은 건이 규명·조치됐으면 여기서 끊습니다

메일은 이 두 가지를 시험하기 위한 재료입니다. 분위기용이 아닙니다.

## 반드시 지킬 것 — 사내 정보 금지

이 프로젝트는 공개 데이터셋(VisA)과 가상 데이터만 씁니다.

- 메일 도메인은 `@example.com` 만 씁니다
- 사람 이름은 `김공정`, `이품질` 같은 가상명. 사번은 쓰지 않습니다
- 회사는 `가상제조 주식회사`, 팀은 `검사기술팀` 정도로 일반화합니다
- 라인은 `line_01`~`line_04`, 품목은 VisA 객체명(`capsules`, `pcb1`,
  `macaroni1` 등)을 씁니다
- 결함은 `찍힘`, `눌림`, `이물` 같은 일반어만. 사내 결함 코드는 쓰지 않습니다
- 장비 공급사명, 모델명, 생산 거점, 실제 공정 조건은 언급하지 않습니다

## 메일 성격 배분

전부 잘 쓴 메일이면 접수 단계가 검증되지 않습니다. 아래처럼 섞어 주세요.

| 성격 | 무엇을 보는가 |
|---|---|
| 잘 쓴 첫 메일 | 정상 경로 |
| 라인·품목·첨부 중 하나가 빠진 메일 | 되묻는가 |
| 전달(Fwd)·인용(`>`) 스레드 | 인용문에서 엉뚱한 값을 뽑지 않는가 |
| 해결된 과거 건이 인용된 전달 | 중복으로 끊는가 |
| 두 가지 건이 한 메일에 섞임 | 하나만 골라 처리하는가 |
| 야간에 급히 친 메모 | 거친 문장을 처리하는가 |

## 출력 형식

시나리오 YAML 의 `input:` 블록만 출력하세요. 들여쓰기 6칸부터 시작합니다.

```yaml
    input:
      issue_text: |
        보낸사람: 김공정 <gongjeong.kim@example.com>
        받는사람: 검사기술팀 <vision-ops@example.com>
        제목: [2라인] 캡슐 표면 찍힘 미검 건
        보낸시각: 2026-06-07 22:10

        (본문. 사람이 실제로 칠 법한 문장으로)

        --
        김공정 책임
        공정기술 / 가상제조 주식회사

      email:
        from_role: 공정엔지니어      # 실명 아님. 역할만
        thread_depth: 1             # 주고받은 횟수
        has_quoted_history: false   # 인용된 이전 대화가 있는가
        subject_matches_body: true  # 제목과 본문이 같은 건인가

      attachments:
        - line_02/2026-06-05/LOT-20260605-014/img_0142.png
      reporter_role: 공정엔지니어    # email.from_role 과 같은 값
      submitted_at: 2026-06-07T22:10:00
```

`issue_text` 는 반드시 `|` 블록으로 쓰세요. 줄바꿈이 유지되어야 합니다.

메일마다 아래를 짧게 덧붙여 주세요.

- 이 메일이 어떤 인테이크 판정을 노리는가 (`proceed` / `need_more_info` /
  `duplicate`)
- 일부러 빠뜨린 정보가 있다면 무엇인가

## 지어내지 말고 저에게 물어봐 주세요

저는 현장에서 이런 메일을 실제로 받는 사람입니다. **당신이 그럴듯한 메일을
지어내면 시연이 교과서처럼 보입니다.** 심사위원도 현장을 아는 사람일 가능성이
높습니다.

먼저 이런 것들을 물어봐 주세요. 한 번에 다 묻지 말고 두세 개씩.

- 미검출 이슈가 올라올 때 보통 누가 누구에게 보냅니까?
- 접수자가 제일 자주 빠뜨리는 정보는 무엇입니까?
- 제목만 보고는 무슨 건인지 모르는 메일이 얼마나 옵니까?
- 이미 해결된 건이 다시 올라오는 일이 있습니까? 어떤 형태로 옵니까?
- 한 메일에 여러 건이 섞여 오는 일이 흔합니까?
- 급할 때 오는 메일은 평소와 문장이 어떻게 다릅니까?
- 메일 말고 다른 경로(메신저 등)로 오는 경우는 어떤 때입니까?

제 답을 듣고 그것을 메일로 옮겨 주세요. 제가 받은 메일이 재료입니다.

제가 "그냥 만들어줘" 라고 하면 그때는 물어보지 말고 쓰시되, 지어낸 부분에는
`# TODO(장영진): 현장 확인 필요` 주석을 달아 주세요.

## 6. 붙여넣은 뒤에 할 일

1. 나온 `input:` 블록을 `data/scenarios.yaml` 의 해당 시나리오에 넣습니다
2. 커밋하면 형식 검사가 자동으로 돕니다 (1~2분 뒤 커밋 옆에 ✅ 또는 ❌)
3. ❌ 면 메시지를 웹 클로드에 붙여넣어 고쳐 달라고 하시면 됩니다

**들여쓰기가 제일 자주 깨집니다.** `issue_text: |` 아래 본문은 `issue_text`
보다 더 들여써야 하고, 그 안에서는 들여쓰기가 그대로 보존됩니다.

커밋 전에 한 번만 더 봐 주세요 — **실제 도메인이나 실명이 남아 있지
않은지.** 이건 자동 검사가 잡지 못합니다.
