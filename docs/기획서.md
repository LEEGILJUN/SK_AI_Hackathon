## 한 장 요약
배포된 AI 외관검사 모델이 못 잡는 불량을 만났을 때, 원인 진단과 데이터 선별, 메모리 뱅크 재구성, 성능 검증, 배포 패키지 생성까지를 에이전트가 스스로 수행합니다. 검사 모델을 새로 만드는 과제가 아닙니다. 이미 배포된 모델을 계속 살아 있게 유지하는 운영의 문제를 다룹니다.

미검출의 원인은 여섯 가지인데 그중 넷은 재학습으로 해결되지 않습니다. 임계값만 조정하면 될 일을 재학습으로 처리하고, 거리로는 원리적으로 갈리지 않는 결함에 데이터를 계속 넣는 일이 현장에서 반복됩니다. 그래서 이 서비스의 시험대는 재학습을 해야 할 때 하는가가 아니라 하지 말아야 할 때 멈추는가입니다.

판단의 근거는 검사 모델 안에 이미 있습니다. PatchCore는 정상 패치를 메모리 뱅크에 담고 최근접 거리로 판정하므로, 미검출 이미지가 뱅크의 어떤 정상 패치와 가까웠는지를 되짚을 수 있습니다. 진단은 추측이 아니라 추적입니다.

**[표 0] 예선 기간에 재서 확인한 것**
| 확인한 것 | 결과 |
|---|---|
| 실제 언어 모델로 전 구간 실행 | 도구 10개 전부 호출, 순서는 모델이 결정 |
| 진단 규칙의 원인 분류 정확도 | 22/24 (92%) — 규칙만의 값 |
| 임계값 조정의 한계 | AUROC 1.000에 과검 0%인 뱅크가 12건 중 0건 검출 |

| 판독의 병목은 능력이 아니라 위치 | 자리를 주면 80.8%, 엉뚱한 자리면 11% |
| 신구 비교 | 14장 가운데 사람이 확인할 것은 1장 |

경계도 함께 적습니다. 배포 패키지와 승인 요청 문서까지만 만들고 실제 장비 반영은 사람이 합니다. 품질 검사 설비에서 무인 배포는 의도적으로 배제했으며, 그 경계를 코드가 지키는지 시험으로 강제합니다. 데이터는 전부 공개 데이터셋과 가상 생성분이고 사내 데이터는 사용하지 않습니다. 실제 모델을 통과한 진단 정확도는 아직 측정하지 않았으며 본선에서 확인합니다.

## 1. 팀소개

### 1-1. 팀명 및 컨셉
팀 「사람이 병목이다」는 제조 현장에 이미 배포된 AI 외관검사 모델이 "못 잡는 불량"을 만났을 때, 원인 진단부터 데이터 선별, 메모리 뱅크 재구성, 성능 검증, 배포 패키지 생성까지의 전 과정을 에이전트가 스스로 수행하도록 만드는 검사 AI 자율 운영 서비스입니다. 현장 엔지니어가 "이 불량을 못 잡는다"고 문제를 제기하는 순간부터, 개선된 모델과 검증 리포트가 승인 대기 상태로 올라오기까지를 하나의 닫힌 루프로 연결합니다.

팀명에 문제 인식을 그대로 담았습니다. 담당자가 느려서 대응이 늦어지는 것이 아니라, 작업이 서로 다른 시간대의 사람 사이를 오가면서 발생하는 대기가 리드타임의 대부분을 만듭니다. 제조업의 AI 외관검사는 도입 단계를 넘어 운영 단계에 들어섰지만, 배포된 모델을 계속 살아 있게 유지하는 일은 여전히 소수 전문가의 수작업과 개인의 기억에 의존합니다. 「사람이 병목이다」는 검사 모델을 새로 만드는 것이 아니라, 검사 모델을 운영하는 일 자체를 AI에게 맡기는 문제에 도전합니다.

### 1-2. 팀원 소개 및 주요 역할

**에이전트 담당 — LLM·에이전트·추론**
제조 공정의 AI 외관검사 모델 개발과 현장 운영을 담당해 왔습니다.
- 언어 모델과 시각 언어 모델 실행 환경 구축
- 다섯 에이전트 오케스트레이션과 도구 호출 인터페이스 설계
- PatchCore 추론 파이프라인과 최근접 패치 역추적 구현
- 진단 판정 로직과 근거 리포트 형식
- 데모 환경 구축과 시연 안정화, 기획서와 피칭 총괄

- 미검출 원인 분류 체계의 현업 타당성 검토와 확정

- 판정 기준 테이블 설계

세 사람의 역량은 겹치지 않고 맞물립니다. 도메인 담당이 무엇이 옳은 판정인지를 정의하고, 데이터 담당이 그 판정에 필요한 근거 데이터를 만들며, 에이전트 담당이 둘을 연결해 에이전트가 실제로 판단하고 실행하는 형태로 통합합니다. 진단 에이전트는 판정 기준과 로직이 분리되지 않으므로 에이전트 담당과 도메인 담당이 함께 진행합니다.

## 2. 문제 정의

### 2-1. 문제의 배경
제조업 전반에서 외관검사에 AI를 도입하는 흐름은 이미 확산 단계에 접어들었습니다. 이상탐지, 분류, 영역 분할 등의 기술이 성숙하면서, 검사 모델을 만들어 라인에 올리는 일 자체는 더 이상 가장 어려운 과제가 아닙니다.

문제는 그다음에 시작됩니다. 검사 모델은 배포된 순간부터 성능이 서서히 열화합니다. 이전에 없던 결함 유형이 새로 출현하고, 공정 조건과 자재 로트가 바뀌며, 조명과 광학계에 미세한 변화가 누적됩니다. 고객이 요구하는 검출 기준이 바뀌기도 합니다. 즉 검사 AI는 한 번 만들고 끝나는 소프트웨어가 아니라, 지속적으로 상태를 살피고 손봐야 하는 설비에 가깝습니다.

그런데 이 유지 루프는 거의 전부 수작업입니다. 현장에서 미검출이 발견되면 담당자에게 메일이나 메신저로 전달되고, 담당자가 이미지를 하나씩 열어 원인을 짐작하고, 학습에 쓸 데이터를 직접 선별하고, 모델을 재학습하고, 여러 단계의 검증을 순차적으로 수행한 뒤, 최종적으로 장비에 반영합니다.

제약은 더 있습니다. 제조 현장의 학습 서버는 보안상 외부와 단절된 폐쇄망에 있고, 검사 장비 공급사가 복수인 경우 알고리즘과 학습 플랫폼, 검사 구조가 서로 달라 하나의 방식으로 통합 자동화하기가 어렵습니다. 그 결과 운영 이력은 표준화되지 못한 채 담당자 개인의 파일과 기억에 남습니다.

정리하면, 검사 모델을 잘 만드는 문제는 상당 부분 풀렸지만 배포된 모델을 계속 살아 있게 유지하는 문제는 여전히 사람이 전부 감당하고 있습니다. 그리고 AI 검사 설비가 늘어날수록 이 부담은 선형으로 증가합니다. 지금 풀지 않으면, 검사 AI를 확대할수록 그것을 돌볼 사람이 부족해지는 구조적 한계에 도달하게 됩니다.

### 2-2. Pain Point
- **접수가 비정형이다** — 어느 영역에서 어떤 유형의 결함이 누락됐는지가 구조화되지 않아, 담당자가 다시 묻고 확인하는 데만 상당한 시간이 듭니다.
- **1차 원인 판단이 숙련자에게 묶여 있다** — 모델 문제인지 설비 조건인지 결함 정의 문제인지를 가르는 판단이 소수의 경험에 의존합니다. 틀리면 불필요한 재학습에 시간을 낭비합니다.
- **데이터 선별이 수작업이다** — 어떤 결함 유형이 몇 장 부족한지조차 사람이 세어 봐야 압니다.
- **검증이 다단계 수작업이다** — 자체 테스트셋 평가, 표준 불량 세트 확인, 시뮬레이터 재검증을 순차로 수행하며 각 단계 결과가 자동으로 축적되지 않습니다.
- **학습 이력이 개인에게 종속된다** — 폴더는 남지만 무엇을 왜 추가했는지는 기록되지 않습니다. 담당자가 바뀌면 다음 사람이 판단할 근거가 사라집니다.
- **거점별 이력이 통합되지 않는다** — 같은 유형의 문제를 다른 거점에서 처음부터 다시 풉니다.
- **대응 총량이 인력 수에 묶인다** — 검사 AI를 확대 적용할수록 대응하지 못하고 밀리는 이슈가 늘어납니다.

다섯 번째 항목은 한 줄로 넘기기 어렵습니다. 모델이 본 데이터의 범위가 곧 모델의 성능 경계입니다. 학습 이력이 없다는 것은 문서 관리 부실에 그치지 않고, 다음 사람이 판단할 근거 자체가 사라진다는 뜻입니다.

두 번째 항목의 비중이 특히 큽니다. 미검출이 발생하면 현장에서 가장 흔히 내려지는 처방이 "학습 데이터를 더 모으자"인데, 원인이 다른 층위에 있으면 데이터를 아무리 늘려도 해결되지 않습니다. 공개 데이터셋에서 입력 해상도와 학습 데이터 양을 하나씩만 바꿔 가며 측정해 보니, 뱅크를 키우는 것만으로는 검출 성능이 오르지 않았고 해상도를 올렸을 때 크게 올랐습니다. 상세한 내용은 3-5절에 정리했습니다.

### 2-3. 병목의 실체: 작업 속도가 아니라 대기 시간
주목할 점은 각 단계의 순수 작업 시간 자체는 길지 않다는 것입니다. 담당자가 실제로 손을 대는 시간은 단계당 3~4시간 수준입니다. 그럼에도 하나의 검출력 이슈가 종료되기까지 훨씬 긴 시간이 걸리는 이유는 다른 데 있습니다.

모든 단계가 서로 다른 시간대에 있는 담당자 사이를 오가기 때문입니다. 현장 거점과 본사의 시차, 그리고 담당자의 가용 시점이 맞물리면서, 작업이 넘어갈 때마다 반나절에서 하루의 대기가 발생합니다. 순수 작업 시간을 모두 합쳐도 하루 남짓인 일이 실제로는 수 주에 걸쳐 진행되는 구조입니다.

**[표 1] 순수 작업은 3~4시간인데 리드타임은 수 주가 된다**
| 단계 | 순수 작업 | As-Is 대기 요인 | 에이전트 적용 후 |
|---|---|---|---|
| 이슈 제기·접수 | 3~4h | 현장에서 담당자로 전달, 시차로 반나절~1일 대기 후 착수 | 제기 즉시 구조화, 대기 없음 |
| 정보 보완 요청·회신 | 1~2h | 담당↔현장 왕복 2회 내외, 왕복당 약 1일 | 접수 시점에 부족 항목을 즉시 질의 |
| 원인 판단 | 3~4h | 숙련자의 가용 시점에 종속 | 자동 판정 및 근거 제시 |
| 데이터 선별·확보 | 3~4h | 현지 협조 필요, 왕복당 약 1일 | 보유 데이터 자동 탐색, 부족분만 요청 |
| 재학습 | GPU 시간 | 대기 없음 | 동일 |
| 검증 3단계 | 3~4h | 순차 수작업, 단계 간 결과 수동 이관 | 성능 검증 자동 평가 및 신구 비교 |
| 배포 준비·승인 | 1~2h | 승인자 가용 시점에 종속 | 패키지 사전 생성, 승인만 대기 |

표에서 드러나듯 병목은 사람의 작업 속도가 아니라 왕복 횟수입니다. 따라서 개선의 대상도 "사람을 더 빠르게 일하게 하는 것"이 아니라 "대기 구간 자체를 없애는 것"이어야 합니다. 에이전트는 시차의 영향을 받지 않고 상시 동작하므로, 이 문제에 정확히 대응합니다.

이 문제들을 해결하면 이슈 제기부터 개선 모델 적용까지의 리드타임이 단축되고, 같은 인원으로 처리 가능한 이슈 건수가 늘어나며, 개선 이력이 개인이 아닌 조직의 자산으로 축적됩니다. 나아가 검사 AI 적용 확대의 속도가 인력 증원 속도에 종속되지 않게 됩니다.

## 3. 서비스 개요

### 3-1. 대상 고객
직접 사용자는 두 축입니다. 하나는 검사 AI를 운영하는 AI 담당자로, 검출력 이슈에 대응해 모델을 개선하고 배포하는 주체입니다. 다른 하나는 생산 현장의 공정·품질 엔지니어로, 미검출을 최초로 발견하고 문제를 제기하는 주체입니다.

최종 수혜자는 품질 조직과 생산 조직입니다. 품질 조직은 검출력 이슈가 며칠 안에 닫히는 것을 확인할 수 있고, 생산 조직은 검사 성능 저하로 인한 재검사와 후공정 부하를 줄일 수 있습니다. 경영 관점에서는 검사 AI 적용 범위를 인력 증원 없이 확대할 수 있게 됩니다.

### 3-2. 주요 기능
서비스는 다섯 개의 에이전트가 순차적으로 협업하는 구조로 구성됩니다. 각 에이전트는 정해진 절차를 기계적으로 밟지 않습니다. 주어진 정보로 판단하고, 다음 단계로 넘길지를 스스로 결정합니다. 아래 표의 "판단하는 것" 항목이 각 에이전트의 존재 이유입니다.

**[표 2-1] 다섯 에이전트가 각각 무엇을 판단하는가**
| 에이전트 | 입력 | 판단하는 것 | 출력 |
|---|---|---|---|
| 이슈 접수 | 현장의 자연어 이슈 | 정보가 충분한가, 과거에 해결된 유사 사례인가 | 구조화된 이슈, 유사 사례 목록 |
| 진단 | 미검출 이미지, 이상 점수, 최근접 패치 | 임계값·뱅크 오염·커버리지·설비·기준 중 무엇인가 | 원인 분류와 근거, 재학습 진행 여부 |
| 데이터 선별 | 원인 분류 결과와 조건 | 뱅크에 무엇을 넣고 무엇을 빼야 하는가 | 재구성 대상 목록, 추가 수집 요청서 |
| 학습·평가 | 재구성된 정상 데이터셋 | 성능 검증을 통과했는가, 통과하지 못했다면 원인은 무엇인가 | 신규 뱅크, 신구 비교 리포트 |
| 릴리즈 | 성능 검증 통과 뱅크 | 배포 가능한 상태인가, 승인에 필요한 근거는 무엇인가 | 배포 패키지, 변경 이력, 승인 요청 |

진단 에이전트는 이 서비스의 핵심입니다. 기준 모델은 현행 검사 시스템과 동일한 PatchCore를 사용합니다. PatchCore는 정상 이미지의 패치를 메모리 뱅크에 담아두고 최근접 거리로 이상 점수를 산출하는 구조이므로, 미검출이 발생했을 때 해당 이미지가 뱅크의 어떤 정상 패치와 가까웠는지를 그대로 되짚을 수 있습니다. 판단의 근거가 모델 내부에 이미 존재한다는 뜻이며, 진단 에이전트는 추측하지 않고 추적합니다. 이 구조가 과제의 기술적 토대입니다.

원인을 가르는 근거는 일곱 가지 판별 항목의 조합입니다. 결함이 이미지에 실제로 보이는가, 화질 지표가 기준 분포를 벗어났는가, 이상 점수가 임계값 대비 어느 위치인가, 최근접 정상 패치가 무엇인가, 그 패치가 실제로 정상인가 아니면 잘못 포함된 결함인가, 현재 조건의 정상 패치가 뱅크에 포함되어 있는가, 그리고 판정 기준상 불량이 맞는가입니다. 첫 번째와 다섯 번째만 시각 언어 모델의 판독을 사용하고 나머지는 조회와 계산으로 정확한 값을 얻습니다. 진단의 신뢰도는 인상 판단이 아니라 이 정량 근거에서 나옵니다.

시각 언어 모델을 쓰는 두 항목에는 구현상의 전제가 하나 있습니다. 전체 이미지를 그대로 보여 주고 판독을 요청하면 정확도가 크게 떨어집니다. 원본에서 전체 면적의 0.1% 수준인 결함은 전체 화면 안에서 묻힙니다. 따라서 판독은 항상 관심 영역을 잘라 확대한 뒤 수행합니다. 확신도가 낮으면 모델이 판단을 보류하도록 하고, 그 경우 시스템은 해당 항목을 근거에서 제외하고 사람에게 확인을 요청합니다.

관심 영역의 위치는 정답 마스크가 아니라 PatchCore의 이상 점수만으로 짚습니다. 실제 운영에는 정답 마스크가 없기 때문이며, 한 품목에서는 이 방식이 마스크로 자른 경우보다 오히려 나았습니다. 다만 품목에 따라 결과가 갈립니다.

갈림의 원인이 판독 모델인지 위치 추정인지를 가르려고 대조군을 두었습니다. 12개 카테고리 전체에 정답 마스크로 잘라 물었을 때와, 결함이 없는 조각을 같은 크기와 같은 프롬프트로 물었을 때를 비교했습니다.

**[표 2-2] 자리를 주면 80.8%, 엉뚱한 자리를 주면 11%**
| 잘라 준 조각 | 결함이 보인다고 답한 비율 | 건수 |
|---|---|---|
| 정답 마스크로 자른 조각 (결함 있음) | 80.8% | 97/120 |
| 정상 이미지에서 무작위로 자른 조각 | 10.8% | 13/120 |
| 결함 이미지에서 결함을 비껴 자른 조각 | 11.0% | 13/118 |

자리를 정확히 주면 80.8%, 엉뚱한 자리를 주면 11% 안팎으로 7.4배가 갈립니다. 두 대조군이 거의 같은 값이라는 점도 중요합니다. 결함 이미지든 정상 이미지든 결함이 없는 자리를 주면 같게 답하므로, 확대된 조각이면 무조건 결함이라고 답하는 것이 아니라 실제로 결함을 보고 답한다는 뜻입니다. 판독 능력 자체는 문제가 아니며, 정확한 위치를 주면 기판에서도 캡슐보다 높게 나옵니다.

병목은 위치 추정 쪽입니다. 기판 계열에서는 이상 히트맵이 결함 자리를 짚지 못해, 역추적으로 지정한 조각으로는 열 건 중 세 건에 그쳤습니다. 상위 자리를 다섯 배로 늘려도 네 건, 자리별 기준선을 빼도 다섯 건으로 5할을 넘지 못했습니다. 다만 자리를 놓치면 11%만 결함이 보인다고 답하므로, 열 건 중 세 건은 우연이 아니라 자리를 세 번 맞혔다는 뜻입니다. 좌표가 기판의 특정 행에 몰리는 경향이 관측되어 구조물의 영향으로 보입니다. 자리별 기준선을 빼는 보정은 이미 5할을 넘지 못해 후보에서 제외했고, 남은 후보인 특징 추출기 교체가 이 병목에 닿는지를 본선까지 검증합니다. 후보를 좁힌 과정은 3-5절에 정리했습니다.

판별 1번을 해결됐다고 쓰지 않는 이유가 여기 있습니다. 프로토타입의 가상 공장이 기판 품목이고, 이 때문에 진단이 보류된 사례가 나왔습니다. 그래서 판별 항목을 일곱 개로 두고 하나가 빠져도 나머지로 판정이 성립하도록 설계했습니다.

네 번째와 다섯 번째 항목은 함께 움직입니다. 최근접 정상 패치를 찾아내는 것만으로는 부족하고, 그 패치가 실제로 결함인지 아니면 진짜 정상품인지를 구분해야 원인이 갈리기 때문입니다. 결함이 잘못 포함된 것이라면 뱅크 오염이고, 진짜 정상품인데 신규 결함과 형상이 유사한 것이라면 전혀 다른 문제입니다.

**[표 2-3] 여섯 원인 가운데 넷은 뱅크 재구성이 답이 아니다**
| 원인 | 판별 방법 | 조치 | 재구성 | 규칙 정확도 |
|---|---|---|---|---|
| 임계값 문제 | 이상 점수는 높으나 임계값 아래에 위치 | 임계값 재조정 | 불필요 | 4/4 |
| 뱅크 오염 | 최근접 정상 패치를 확인한 결과 실제로는 결함 | 오염 샘플 제거 후 뱅크 재구성 | 필요 | 4/4 |
| 커버리지 부족 | 현재 조건의 정상 패치가 뱅크에 없음 | 해당 조건 정상 이미지 추가 | 필요 | 4/4 |
| 정상 분포 중첩 | 최근접 패치가 진짜 정상품이며 형상이 유사 | 기준 재정의, 전용 판별 로직, 촬영 조건 개선 | 효과 없음 | 2/4 |
| 설비·광학 | 화질 지표가 기준 분포를 이탈 | 설비 점검 요청 | 차단 | 4/4 |
| 기준 문제 | 검출은 했으나 기준상 양품으로 분류 | 판정 기준 재정의 요청 | 차단 | 4/4 |

오른쪽 끝의 정확도는 시나리오 24건의 정답 근거를 진단 규칙에 입력해 원인을 대조한 결과입니다. 이미지, 메모리 뱅크, 조회 계층, 시각 언어 모델을 일절 사용하지 않았으므로 규칙 자체의 정확도이며, 전체로는 24건 중 22건이 일치했습니다. 실제 모델을 사용한 진단 정확도는 아직 측정하지 않았고 본선에서 확인합니다. 틀린 2건의 성격은 3-5절에서 다룹니다.

여섯 원인 가운데 넷은 뱅크를 다시 만드는 것이 답이 아닙니다. 특히 임계값 문제는 값만 조정하면 되는 사안이므로, 이를 재학습으로 처리하고 있었다면 그 자체가 상당한 낭비입니다. "무엇을 학습시킬까"가 아니라 "학습시킬 문제가 맞는가"를 먼저 판단한다는 점이 기존 도구와의 결정적 차이이며, 진단 성능의 시험대는 재학습을 해야 할 때 하는가에 있지 않습니다. 하지 말아야 할 때 멈추는가에 있습니다.

뱅크 오염은 실무적으로 가장 다루기 어려운 원인입니다. 정상 학습 데이터에 불량이 섞여 들어가면 그와 유사한 불량이 전부 정상으로 판정되는데, 사람이 원인을 규명하려면 상당한 시간이 걸립니다. 최근접 패치 역추적은 이 문제를 즉시 규명하며, 에이전트의 가치가 가장 선명하게 드러나는 지점입니다.

정상 분포 중첩은 성격이 전혀 다릅니다. 뱅크는 깨끗하고 최근접 패치도 진짜 정상품인데, 새로 정의된 결함이 정상 변동 범위 안에 들어가 있어 거리 기반으로는 원리적으로 구분되지 않는 경우입니다. 이때는 데이터를 더 넣어도 해결되지 않습니다. 해당 결함을 뱅크에 넣으면 오히려 더 못 잡게 되고, 유사한 정상 패치를 제거하면 진짜 정상품에서 과검이 발생합니다. 진단 에이전트는 임계값을 낮춰가며 검출률과 과검률의 관계를 산출하여 임계값 조정만으로는 해결되지 않음을 정량적으로 제시하고, 판정 기준 재정의나 전용 판별 로직 추가, 촬영 조건 개선 등 다른 층위의 조치를 권고합니다. 검출 알고리즘의 원리적 한계를 명시적으로 짚어 준다는 점에서, 담당자가 해결되지 않을 재학습을 반복하는 것을 막아 줍니다.

학습 이력 인덱서는 진단의 전제를 만드는 보조 모듈입니다. 재학습 때마다 남은 프로젝트 폴더를 스캔해 모델 버전별 뱅크 구성 프로파일, 즉 어떤 조건의 정상 이미지가 몇 장 포함되었는지를 구조화된 표로 복원합니다. 연속된 두 버전의 뱅크 구성 차이를 비교하면 당시의 재학습 의도까지 상당 부분 역추정할 수 있습니다. 다만 역추정 결과는 근거와 함께 추정으로 명시하고, 담당자가 확인한 경우에만 확정 이력으로 승격합니다. 이후의 재학습에 대해서는 촉발 이슈, 진단 원인, 학습셋 변경 내역, 평가 결과, 배포 시점이 자동으로 기록되므로 같은 문제가 반복되지 않습니다.

학습·평가 에이전트는 홀드아웃 데이터셋과 표준 불량 세트 평가에 더해, 신규 뱅크를 실제 판정에 사용하지 않고 병렬로만 추론시키는 신구 비교를 수행합니다. 기존 뱅크와 판정이 갈리는 케이스만 추출하므로, 정답 확인이 필요한 이미지 수를 대폭 줄이면서도 실제 검출력 변화를 정량적으로 비교할 수 있습니다.

릴리즈 에이전트는 배포 패키지와 승인 요청 문서까지만 생성하고, 실제 장비 반영은 사람의 승인을 거치도록 설계했습니다. 품질 검사 설비의 특성상 무인 배포는 의도적으로 배제했으며, 승인 이전까지의 모든 준비 작업을 자동화하는 것이 목표입니다. 담당자가 화면에서 승인하면 승인자와 시각, 사유가 기록되고 뱅크를 전환하는 명령이 실제 폴더 이름으로 제시됩니다. 그 명령을 실행하는 것은 사람입니다. 승인 버튼이 배포를 실행하지 않는다는 경계가 코드와 시험으로 강제됩니다.

**이슈가 접수되지 않아도 스스로 도는 경로**
서비스는 두 가지 방식으로 시작합니다. 하나는 현장이 미검출을 발견해 이슈를 제기하는 경우이고, 다른 하나는 아무도 제기하지 않아도 스스로 도는 경우입니다. 예약 스케줄러는 지정된 시각에 아직 검사하지 않은 생산분을 점검하고, 미검 의심 건을 찾으면 이슈를 만들어 넣습니다. 이후 진단, 데이터 선별, 뱅크 재구성 후보 생성, 성능 검증 평가, 신구 비교까지 자동으로 진행한 뒤 승인 요청 문서에서 멈춥니다.

여기서 중요한 설계 결정은 자동 점검용 진단 경로를 따로 만들지 않았다는 점입니다. 경로가 두 벌이 되면 한쪽만 고쳐집니다. 시연에서 되던 것이 실제 운영에서 안 되는 상황이 생깁니다. 그래서 스케줄러가 만드는 이슈도 사람이 접수한 것과 동일한 형식의 자연어이며, 제품 식별자가 본문 안에 포함됩니다. 언어 모델이 원문에서 항목을 뽑아내는 경로를 그대로 지나야 합니다.

스케줄러가 생성하는 이슈는 다음과 같은 형태입니다. "1라인 야간 생산분 자동 점검에서 미검 의심 건이 나왔습니다. 제품 PCB1-PEND-000이며 이상 점수 0.005로 임계값 2.20 아래입니다."

한 번에 처리하는 건수는 5건으로 제한하고, 남은 건수를 보고서에 함께 적습니다. 신구 비교의 논거가 판정이 갈린 건만 확인하면 되므로 검증 공수가 줄어든다는 것인데, 한 번에 수백 건을 올리면 그 논거가 무너집니다.

언어 모델을 실제로 붙여 전 구간을 돌려 보았습니다. 접수부터 이슈 접수, 생산 정보 조회, 추론, 판별 일곱 항목, 진단, 데이터 선별, 뱅크 재구성, 성능 검증 평가, 신구 비교, 승인 요청 생성까지 도구 열 개가 전부 호출되었고, 호출 순서는 정해진 절차가 아니라 모델이 정했습니다. 단일 GPU에서 151초가 걸렸으며 사람이 버튼을 누른 곳도, 배포된 것도 없었습니다. 여기까지가 전 구간이 순서대로 실행된다는 확인입니다. 판정 정확도는 본선까지 검증합니다.

이 실행에서 차별화의 근거 하나가 드러났습니다. 같은 이미지와 같은 점수에서 판별 5번의 답만 바꿔 두 번 돌렸더니, 최근접 패치가 진짜 정상품이라고 답한 경우에는 임계값 문제로 진단하고 뱅크를 건드리지 않았으며, 잘못 들어간 결함이라고 답한 경우에는 뱅크 오염으로 진단하고 재구성을 지시했습니다. 판별 항목 하나가 원인과 조치를 정반대로 돌립니다.

### 3-4. 차별화 포인트
기존 방식과 대조하여 일곱 가지로 정리합니다. 이 과제의 혁신성은 새로운 검출 알고리즘에 있지 않고, 지금까지 자동화 대상으로 다뤄지지 않던 원인 진단을 자동화한 데 있습니다.

**① 기록하는 도구가 아니라 판단하는 에이전트**
기존 MLOps 도구는 사람이 실행한 작업을 기록하고 추적하는 데 초점이 있습니다. 무엇을 학습시킬지, 결과가 배포할 만한지는 여전히 사람이 판단합니다. 이 서비스는 그 판단 자체를 에이전트가 수행합니다. 특히 미검출의 원인을 임계값·뱅크 오염·커버리지 부족·설비·기준으로 가르는 1차 진단은 지금까지 자동화 대상으로 다뤄진 적이 거의 없는 영역입니다.

판단을 명시적으로 정의한다는 것에는 부수적이지만 결정적인 효과가 있습니다. 판별 항목 일곱 개를 전수 조사한 결과 두 항목이 사실상 고정된 값을 돌려주고 있었음을 발견했습니다. 값이 나오기 때문에 화면에서는 정상으로 보였고, 눈으로 보는 것만으로는 알 수 없었습니다. 각 항목이 무엇을 입력으로 받아 무엇을 근거로 판정하는지를 기록해 두었기 때문에 조사가 가능했습니다.

사람이 수작업으로 판단하는 현재 상태가 정확히 그 상태입니다. 무엇을 근거로 판단했는지가 남지 않으면, 작동하지 않는 판단이 작동하는 것처럼 보인 채로 계속 운영됩니다. 판단을 자동화한다는 것은 사람을 대체한다기보다, 판단의 근거를 검사 가능한 형태로 만드는 일에 가깝습니다.

**② 모델 내부에 이미 존재하는 근거를 진단에 활용**
PatchCore는 정상 패치를 메모리 뱅크에 담아두고 최근접 거리로 판정하는 구조이므로, 미검출 이미지가 어떤 정상 패치와 가까웠는지를 역추적할 수 있습니다. 별도의 설명 모델을 붙이는 것이 아니라 검사 모델이 원래 가지고 있던 정보를 판단 근거로 쓴다는 점에서, 추가 비용 없이 설명 가능성을 확보합니다.

임계값 스윕과 나란히 놓으면 이 차별점이 왜 결정적인지 드러납니다. 깨끗한 뱅크와 결함 세 장을 섞은 뱅크를 같은 홀드아웃으로 비교했습니다.

**[표 2-5] AUROC 1.000에 과검 0%인 뱅크가 12건 중 0건을 잡는다**
| 뱅크 | AUROC | 임계값 스윕 판정 | 운영 임계값에서 검출 |
|---|---|---|---|
| 깨끗한 뱅크 | 1.000 | 해결 가능 (과검 0.0%) | - |
| 오염된 뱅크 | 1.000 | 해결 가능 (과검 0.0%) | 12건 중 0건 |

측정 조건은 다음과 같습니다. VisA pcb1, 입력 512 정사각, 뱅크 정상 150장에 결함 3장 혼입(혼입률 2.0%), coreset 0.01, 홀드아웃은 정상 50장과 결함 12장입니다. AUROC는 홀드아웃 구성이 다르면 직접 비교할 수 없으므로 조건을 함께 적습니다.

두 지표가 모두 만족합니다. AUROC는 1.000이고 스윕도 임계값을 내리면 과검 없이 전건을 검출할 수 있다고 답합니다. 그런데 그 뱅크는 운영 임계값에서 12건 가운데 한 건도 잡지 못합니다. 혼입된 결함이 이상 점수를 24% 끌어내렸고, 전건이 임계값 아래로 내려갔습니다.

스윕이 틀린 답을 준 것은 아닙니다. 임계값을 내리면 검출은 실제로 회복됩니다. 문제는 그 답이 원인을 고치지 않는다는 점입니다. 혼입 이미지는 뱅크에 그대로 남고, 다음에 또 섞이면 임계값을 또 내려야 합니다. 그리고 그 답은 원인이 정말 임계값 문제일 때와 완전히 같습니다. 두 원인의 조치는 정반대인데도 그렇습니다. 스윕은 문제를 못 푸는 쪽이 아닙니다. 푼 줄 알게 만듭니다. 지표가 전부 통과인데 현장에서는 전건 미검인 상태를 만든다는 점에서, 이쪽이 훨씬 위험한 실패입니다.

갈리는 것은 최근접 패치 역추적입니다. 미검출 12건의 최근접 패치 출처를 세었더니 12건 전부가 혼입 이미지를 지목했고, 상위 세 자리가 모두 혼입 이미지였으며 정상 이미지는 한 번도 끼지 않았습니다.

다른 품목에서는 12건 가운데 한 건도 혼입 이미지를 지목하지 않았는데, 이것은 반례가 아니라 옳은 동작입니다. 그쪽에서는 뱅크 오염이 이상 점수를 끌어내리지 않았습니다. 그 12건의 미검출은 뱅크 오염 탓이 아니었습니다. 뱅크에 결함이 섞여 있다는 이유만으로 뱅크 오염이라 진단하지 않는다는 뜻이며, 이것이 하지 말아야 할 때 멈추는가에 대한 실증입니다. 반복 지목은 뱅크 오염이 실제로 이상 점수를 끌어내린 경우에 성립하고, 섞여 있어도 판정에 영향을 주지 않았다면 지목되지 않습니다.

한 단계가 더 붙습니다. 최근접 패치를 찾아내는 것만으로는 부족하고, 그것이 잘못 들어간 결함인지 진짜 정상품인지를 갈라야 원인이 정해집니다. 앞이면 뱅크 오염이라 제거 후 재구성해야 하고, 뒤면 정상 분포 중첩이라 재구성하면 안 됩니다. 뱅크에서 실제로 결함 위에 있는 패치와 진짜 정상부 패치를 각각 골라 시각 언어 모델에 물어 이 갈림이 서는지 확인했습니다. 정상부 패치를 결함으로 오판한 사례가 한 번도 없었다는 점이 실질적으로 더 중요합니다. 정상 패치를 결함으로 오판하면 멀쩡한 이미지를 뱅크에서 빼게 되는데, 되돌리기 어렵고 검사 범위를 깎으며, 뱅크 오염을 고치려다 여섯 원인 가운데 하나인 커버리지 부족을 스스로 만드는 일이 됩니다.

질문을 던지는 방식도 함께 점검했습니다. 패치를 물을 때 이것이 정상으로 등록된 것이라는 전제를 모델에게 알려주는데, 그 전제가 답을 정상 쪽으로 끌 위험이 있어 방어 문장을 넣어 두었습니다. 전제를 뺀 프롬프트와 비교해 보니 유도는 없었고 오히려 반대쪽이 위험했습니다. 전제 없이 결함이 보이느냐고만 물으면 모델이 무언가를 찾으려 들어 멀쩡한 정상 표면에서 없는 결함을 만들어냈습니다. 그대로 조치했다면 정상 이미지를 뱅크에서 뺐을 것입니다.

**③ 정답 없는 양산 데이터에서 성능을 비교하는 신구 비교 방식**
신규 모델을 배포하면 기존 모델은 더 이상 동작하지 않으므로 동일 조건 비교가 불가능하고, 양산 데이터에는 정답 라벨이 없다는 근본적 제약이 있습니다. 두 모델을 병렬로 추론시켜 판정이 갈리는 케이스만 선별해 확인하는 방식은 이 두 문제를 동시에 우회합니다. 검증 공수를 줄이면서 모델 교체의 실제 영향을 정량화하는 실무적 해법입니다.

14장을 새 뱅크와 기존 뱅크에 병렬로 추론했더니 판정이 갈린 것은 한 장이었습니다. 그 한 장은 이상 점수가 2.135에서 2.969로 올라 미검출에서 검출로 바뀌었고, 새로 놓친 것은 없었습니다. 혼입 이미지를 제거한 것이 실제로 효과를 냈다는 사실을 정답 라벨 없이 보여주며, 사람은 갈린 한 장만 확인하면 됩니다.

**④ 개선 대상을 작업 속도가 아닌 대기 시간으로 재정의**
대부분의 자동화 시도는 사람의 작업을 더 빠르게 만드는 데 집중합니다. 그러나 표 1에서 확인했듯 실제 병목은 시차와 핸드오프로 인한 대기입니다. 에이전트는 시간대에 구애받지 않고 상시 동작하므로, 작업 속도를 개선하지 않고도 리드타임을 단축할 수 있습니다.

**⑤ 사라지는 학습 이력을 복원하고, 이후 이력은 스스로 쌓입니다**
기록이 남아 있지 않은 과거 이력을 폴더 구조와 파일명에서 역추적해 학습셋 프로파일로 복원합니다. 아무것도 없는 상태에서 새로 기록을 시작하는 것이 아니라, 이미 존재하지만 구조화되지 않은 자산을 활용한다는 점에서 도입 장벽이 낮습니다.

복원만으로는 절반입니다. 승인이 끝나면 그 건이 이슈 이력에 한 줄로 쌓이고, 다음에 같은 라인에서 같은 증상이 올라올 때 접수 단계가 그 기록을 찾아 중복인지 판단합니다. 어떤 이슈에 어떤 원인으로 무엇을 왜 바꾸었는지, 누가 언제 승인했는지, 그때 임계값과 뱅크 설정이 무엇이었는지가 함께 남습니다. 문서를 만드는 것과 이력이 쌓이는 것은 다릅니다. 승인 요청 문서가 폴더에 파일로 남아도 다음 이슈가 올라왔을 때 아무도 찾아보지 않으면 자산이 아닙니다. 조회되는 자리에 들어가야 합니다.

**⑥ 공급사에 종속되지 않는 벤더 중립 계층**
검사 장비 공급사는 모델과 학습 플랫폼을 제공하지만, 배포 이후의 운영 루프는 고객의 몫으로 남습니다. 이 서비스는 특정 공급사의 알고리즘에 종속되지 않는 중립 계층으로 동작하여, 서로 다른 공급사의 장비가 혼재하는 환경에서도 동일한 판단 기준과 이력 체계를 적용합니다.

**⑦ 배포를 막는 것과 되돌릴 수 있게 하는 것**
승인 요청에서 멈춘다는 것은 문서상의 선언에 그치지 않습니다. 시험으로 강제되는 제약입니다. 예약 스케줄러와 에이전트 코드에 배포로 읽히는 함수가 생기지 않았는지 코드를 파싱해 검사하며, 스케줄러 모듈에만 18개의 시험이 걸려 있습니다. 자동으로 실행되는 경로이므로 사람이 버튼을 누르는 화면보다 이 자리가 위험하고, 그래서 여기에 시험을 두었습니다.

배포를 막는 것만으로는 부족합니다. 재구성한 뱅크의 성능이 나쁘면 어떻게 되돌리는가에 답이 없으면, 배포 후보를 만든다는 말 자체가 성립하지 않습니다. 라인과 품목마다 판을 쌓고, 운영에 쓰는 판을 한 줄로 가리키는 구조를 두었습니다. 폴더 이름에는 버전과 만든 시각, 그리고 설정 지문이 함께 들어갑니다. 지문이 있어서 입력 크기를 바꾸면 옛 판이 이름에서 걸러지는데, 입력 크기를 바꾼 뒤 옛 뱅크가 검사를 통과해 다른 척도로 점수를 내던 일이 있었습니다.

되돌리기는 가리키는 이름 한 줄을 바꾸는 일입니다. 파일은 움직이지 않습니다. 파일이 움직이지 않으므로 도중에 멈춰도 어느 것이 운영본인지 잃지 않고, 되돌린 뒤에도 새 판이 남아 다시 앞으로 갈 수 있습니다.

저장은 자동이고 전환은 사람입니다. 후보는 성능 검증과 신구 비교를 지난 뒤에만 저장소에 올라가며, 운영본을 가리키는 표시는 코드가 바꾸지 않습니다. 그 표시를 바꾸는 순간 실제 판정에 쓰이는 뱅크가 바뀝니다. 그것이 곧 배포입니다. 승인 문서에는 전환 명령이 실제 폴더 이름으로 찍혀 나가고, 승인한 사람이 그것을 복사해 실행합니다. 전 구간을 돌렸을 때도 후보가 저장되고 운영본 표시는 그대로였으며, 승인 없이 전환된 흔적은 없었습니다. 성능 검증 네 항목을 모두 통과했는데도 자동으로 밀지 않습니다.

품질 검사 설비에서 무인 배포를 배제한 것은 설계 결정입니다. 기능의 한계가 아닙니다. 그 결정을 코드가 지키게 만든 것 자체가 근거가 됩니다.

### 3-5. 실측으로 확인된 것
예선 기간 중 설계의 타당성을 검증하기 위해 핵심 판정 로직을 구현하고 공개 데이터셋으로 측정했습니다. 아래는 그 과정에서 확인한 사실이며, 기획의 전제가 실제로 성립하는지를 스스로 점검한 결과입니다. 일부 항목은 입력 전처리를 바꾼 뒤 재측정 중이므로 수치 없이 확인된 사실만 적었습니다.

**무엇을 얼마나 보여주는가가 성능을 좌우한다**
입력 해상도와 학습 데이터 양을 한 번에 하나씩만 바꿔 가며 검출 성능을 측정했습니다. 뱅크를 키우는 것만으로는 성능이 오르지 않았고, 해상도를 올렸을 때 크게 올랐습니다. 낮은 해상도에서는 무작위 판정과 다를 바 없는 수준이었습니다.

결함의 크기가 원인이었습니다. 사용한 데이터의 결함은 원본 기준 약 40×40 화소로 전체 면적의 0.1% 수준인데, 낮은 해상도로 입력하면 특징 격자 한 칸에 결함이 통째로 들어갑니다. 이웃 평균 과정에서 주변 정상 칸들과 섞여 희석됩니다. 검출이 안 되니 데이터를 더 모으자는 처방이 통하지 않는 경우의 실제 모습입니다. 우리 진단 체계가 가려내려는 상황과 구조가 같습니다.

같은 문제가 층을 바꿔 되풀이됩니다. 시각 언어 모델에 원본 전체를 그대로 주면 결함 이미지를 높은 확신도로 정상이라고 답했고, 잘라 확대하면 크게 올랐습니다. 반대로 너무 좁게 자르면 스무 건 전부 무엇을 보는지 모르겠다고 답했습니다. 격자 한 칸만 떼어 주면 제품의 어느 부위인지 알 수 없습니다. 여유를 늘리자 판독이 섰습니다. 낮은 해상도에서 격자 한 칸에 묻힌 것, 전체 화면에서 묻힌 것, 좁은 조각에서 맥락이 사라진 것은 모두 모델에게 무엇을 얼마나 보여주는가의 문제였습니다. 모델을 바꿔서 풀 문제가 아니었습니다.

관행으로 쓰던 전처리에서도 같은 것이 나왔습니다. 입력 전처리가 리사이즈 후 중앙 크롭이었는데, 다른 데이터셋 계열에서 흔히 쓰는 조합을 그대로 가져온 것이고 이 데이터에 맞는 근거는 없었습니다. 가로가 긴 이미지라 중앙을 잘라내면 양옆이 사라집니다. 정답 마스크가 크롭 창 안에 들어오는지 카테고리당 40건씩 세어 보니 한 품목에서는 40건 중 12건이 일부 잘려 나갔고, 다른 품목에서는 완전히 사라진 것도 있었습니다. 사라진 결함은 어떤 모델로도 검출할 수 없습니다. 자르지 않는 정사각 리사이즈로 바꾸었으며, 이 변경으로 앞선 측정 조건이 달라져 해당 수치들을 재측정하고 있습니다.

**작아서 못 보는 것이 아니었다**
결함이 작아서 못 본다는 것이 흔한 진단이고 우리도 그렇게 믿었습니다. 실측이 이를 뒤집었습니다. 12개 카테고리 전부에 원본 이미지를 그대로 주고 결함이 보이는지 물었더니, 가장 작은 결함을 가진 카테고리가 열 건 중 일곱 건으로 가장 높았고 가장 큰 결함을 가진 카테고리가 열 건 중 영 건이었습니다. 결함 면적은 22배 차이가 나는데 상관이 없었고 오히려 약한 역상관이었습니다.

갈리는 축은 배경 복잡도였습니다. 커넥터와 패드가 빽빽한 기판 계열은 평균 0.5건, 단순한 배경에 물체 하나가 놓인 나머지는 평균 5.5건이었습니다. 같은 축이 역추적에서도 나타납니다. 크기를 키우는 방향으로 갔다면 이 값을 보지 못했을 것입니다.

**남은 병목을 후보를 지워 가며 좁혔다**
판별 1번이 기판에서 약하다는 것을 확인한 뒤, 원인 후보를 하나씩 재서 지웠습니다. 크기는 위에서 배제되었습니다.

프롬프트도 배제되었습니다. 질문을 세 가지로 바꿔 같은 이미지에 물었는데, 일반적인 결함 예시를 준 것과 품목별 결함 어휘를 준 것, 거기에 품목별 정상 어휘까지 더한 것 사이에 120건 중 네다섯 건 차이밖에 없었고 과검이 함께 늘어 순이득이 없었습니다. 기판 품목은 오히려 내려갔습니다. 결함 이름을 불러 주어도 큰 화면 안에서 찾지 못한다는 것이며, 어휘가 없어서 못 찾는 것이 아닙니다. 자리를 모릅니다.

자리를 그림에 표시해 주는 길도 막혔습니다. 히트맵을 반투명하게 겹치거나 네모 테두리를 그려 주는 방식을 12품목 24장씩 재봤습니다.

**[표 3-1] 위치를 그려 주면 검출은 14%p 오르고 과검은 30%p 넘게 는다**
| 방식 | 결함 검출 | 정상 과검 |
|---|---|---|
| 원본 그대로 | 49.3% | 0.7% |
| 반투명 겹침 | 63.9% | 31.2% |
| 네모 테두리 | 63.2% | 36.1% |

12개 품목 각각 결함 12장과 정상 12장에 대해 품목별 결함 어휘 프롬프트로 측정했습니다. 검출이 14%포인트 오르는 대가로 과검이 30%포인트 넘게 늘어 쓸 수 없습니다. 겹침과 테두리가 거의 같은 값을 냈다는 점이 중요합니다. 그리는 방식은 상관이 없었습니다. 표시할 자리가 틀렸습니다. 이 현상은 시각 언어 모델 심사자를 속이는 조작 유형 가운데 첫 번째로 정의된 것과 같은 형태이며, 다른 과제에서 보고된 편향이 우리 데이터에서도 나타난 것으로 봅니다. 실패로 보이지만 남은 후보를 하나로 줄였습니다. 그것이 이 측정의 값입니다.

남은 후보는 특징 추출기 하나입니다. 우리와 구조가 같은 최근 연구가 정상 패치를 뱅크에 담고 최근접 거리로 판정하되 특징 추출기만 바꾸었는데, 그 방향이 우리 병목에 닿는지 재보았습니다. 기판 품목에서 크롭이 결함을 담는 비율과 판독 정확도가 함께 올랐고 과검은 거의 그대로였습니다. 다만 표본이 열 장이고 오른 품목이 하나뿐이며, 다른 품목은 움직이지 않았습니다. 다음 단계에 근거가 있다는 것까지만 말할 수 있고, 특징 추출기를 바꾸면 해결된다고 말할 수는 없습니다.

지금 바꾸지 않기로 한 것도 근거를 재서 내린 판단입니다. 특징 추출기를 갈면 뱅크와 임계값, 화질 기준 분포, 지금까지의 실측값이 전부 무효가 되어 시연이 흔들립니다. 남은 기간에 무엇을 건드리고 무엇을 두는지를 근거로 정했으며, 후보를 하나씩 재서 지운 이 과정 자체가 우리가 만들려는 진단 방법론의 예시이기도 합니다. 현장에서 원인을 좁혀 가는 절차와 같습니다.

**뱅크 오염은 통계로 찾히지 않는다**
PatchCore는 메모리 뱅크를 줄이려고 서로 먼 점을 우선 남기는 방식을 씁니다. 오염된 이미지의 패치가 우선 선택되는 것은 맞지만, 실데이터에서는 층이 갈립니다. 혼입 이미지 출신 패치는 뱅크에서 4.4배까지 부풀지만, 실제로 결함 위에 있는 패치는 뱅크의 0.3%에 그칩니다. 혼입률을 합성 실험과 같은 수준으로 맞춰도 결함 위 패치는 1.6%입니다. 끌어올려진 것은 결함이 있는 이미지입니다. 결함 그 자체가 아닙니다. 합성 결함은 뚜렷해 정상 분포에서 멀리 떨어집니다. 실제 결함은 미세해 그만큼 튀지 않습니다.

이미지 단위로 빼면 정상부를 함께 버립니다. 혼입 다섯 장이 뱅크에 남긴 패치 가운데 98.2%가 멀쩡한 표면이며, 그 이미지를 통째로 빼면 그것들도 함께 사라집니다. 뱅크 오염을 고치려다 커버리지 부족을 스스로 만드는 셈입니다.

같은 수치가 판별 5번의 한계도 설명합니다. 역추적은 혼입 이미지를 정확히 지목하지만, 지목된 그 패치 자리는 대개 그 이미지의 멀쩡한 부분입니다. 그래서 그 자리를 잘라 물으면 진짜 정상품이라 답하는데 그 답이 틀린 것도 아닙니다. 한계는 모델에도 위치 추정에도 없습니다. 혼입 이미지 안에서 결함이 차지하는 비중 자체가 작습니다.

뱅크 안에서 이웃이 먼 이미지를 찾는 고립도 방식도 함께 재보았습니다. 조건이 맞으면 정밀도가 100%였지만, 혼입이 많아지면 서로 평범해져 스무 장 가운데 두 장만 후보로 올라왔습니다. 정밀도는 높고 재현율이 낮습니다. 이것이 정확한 서술이고, 그래서 고립도를 단독 근거로 쓰지 않습니다. 찾아내는 쪽은 미검출 건들의 반복 지목입니다. 이것이 이 서비스가 통계적 이상 탐지와 갈라지는 지점입니다.

**품목이 다르면 뱅크도 달라야 한다**
한 품목의 뱅크로 다른 품목을 판정해 봤습니다. 두 품목은 같은 보드의 앞면과 뒷면이라 배경과 조명이 같은데도, 뒷면의 멀쩡한 기판이 앞면의 진짜 결함보다 높은 점수로 찍혔습니다. 배경 탓이 아닙니다. 정상 패치 자체가 다르다는 것 하나로 원인이 좁혀집니다.

품목마다 뱅크를 따로 가져가는 근거가 여기 있습니다. 다른 라인의 같은 증상을 중복으로 처리하면 안 되는 근거이기도 합니다. 한 라인의 뱅크가 오염되었다고 해서 다른 라인도 그렇다는 뜻이 아닙니다. 뒤집으면 위험 신호이기도 합니다. 품목을 잘못 물면 전 건이 불량으로 뜨는데, 요란하게 틀리므로 알아채기는 쉽습니다.

**조용히 틀리는 답이 가장 위험하다**
같은 코드가 합성 데이터에서는 통과하고 실제 규모의 데이터에서 실패하는 일이 있었습니다. 원인은 로트 크기 하나였습니다. 조회 계층의 기본 상한이 50건인데 실제 로트는 100장이고, 목록이 정상을 먼저 담기 때문에 잘리면 결함부터 사라집니다. 로트 74장 가운데 50장만 전달되어 결함 여섯 장이 전부 빠졌고, 파이프라인은 미검출이 없다고 답했습니다. 틀린 답인데 오류가 아니라 정상 응답으로 나옵니다.

대응은 상한을 없애는 쪽이 아닙니다. 상한에 닿았다는 사실을 결과에 함께 적습니다. 조용히 잘라내면 받는 쪽에서는 그것이 전부라고 읽습니다. 또한 실제 운영 규모의 데이터를 이미지 없이 생성해 시험에 포함시켜, 규모 때문에 갈리는 문제를 개발 단계에서 먼저 잡도록 했습니다.

임계값을 옮기면 무엇이 달라지는지도 쟀습니다. 임계값에 따라 진단 원인이 달라 보이는데, 정확히 말하면 달라지는 것은 답이 아니라 진단의 대상입니다. 임계값이 미검출로 걸리는 장수를 바꾸고, 그래서 대표로 뽑히는 이미지가 달라지며, 다른 이미지는 최근접 패치가 다르니 원인도 다릅니다. 입력이 바뀐 것입니다. 판정이 흔들린 것과는 다릅니다. 같은 이미지를 놓고 임계값만 바꾸면 원인이 그대로인가는 아직 측정하지 않았고, 안 잰 것을 잰 것처럼 쓰지 않기 위해 화면에서도 그 주장을 뺐습니다.

이 측정 자체가 논거가 됩니다. 임계값을 어느 쪽으로 옮겨도 뱅크에 섞여 들어간 결함은 섞인 채로 남습니다. 내리면 과검이 늘어 볼 것이 없어지고 올리면 미검출이 늘어 원인이 임계값 문제로 바뀝니다. 증상이 옮겨 다닐 뿐 원인이 없어지지 않습니다. 그리고 멈추는 자리가 둘이었는데 이유가 서로 달랐습니다. 한쪽은 과검이 너무 많아 진단할 미검출이 없어서 멈추었고, 다른 쪽은 미검출을 찾았으나 그 이미지에서 결함이 확인되지 않아 원인을 판정하지 않았습니다. 둘 다 고장이 아닙니다. 모르면 멈춘다는 원칙이 서로 다른 자리에서 나타났습니다.

**진단 규칙의 현재 정확도와 남은 과제**
표 2-3의 정확도는 규칙만으로 측정한 값입니다. 원인 일치는 24건 중 22건, 재구성 여부 일치도 22건, 재구성이 답이 아닌 케이스에서 재구성을 지시한 사례는 0건이었습니다. 마지막 값이 0인 것은 원인과 조치의 대응이 표로 고정되어 구조적으로 그렇게 되도록 만들었기 때문이므로, 실험으로 달성했다기보다 설계로 보장한다고 쓰는 쪽이 정확합니다.

틀린 2건은 둘 다 정상 분포 중첩입니다. 초기 측정에서는 임계값 문제와 정상 분포 중첩의 갈림에서 다섯 건이 틀렸는데, 두 원인의 점수 비율 구간이 겹쳐 비율만으로는 원리적으로 갈리지 않는다는 것이 원인이었습니다. 시나리오에 임계값 스윕 결과 필드를 추가해 그 갈림을 해소했고, 그 수정으로 세 건이 바로잡혔습니다.

남은 2건은 성격이 다릅니다. 두 건 모두 결함이 눈에 보이지 않는 경우로 표시되어 있는데, 현재 규칙은 이때 접수 오류 가능성을 고려해 판정을 보류합니다. 판별 1번이 결함을 확인하지 못하면 진단 자체를 멈추는 설계이며, 모르면 멈춘다는 원칙이 적용된 결과이기도 합니다. 다만 정상 분포 중첩은 결함이 정상 변동 범위 안에 있어 눈으로도 확인이 어려운 유형이므로, 이 조합에서 보류가 옳은 동작인지는 분류 체계 차원의 판단이 필요합니다. 도메인 담당자와 확인 중입니다.

정확도를 높이기 위해 규칙을 정답에 맞추면 측정 자체가 무의미해지므로, 현재 값을 그대로 두고 원인을 밝힌 상태로 본선에 들어갑니다.

### 4-2. 프로토타입 범위
본선 기간에는 이슈 접수부터 진단, 데이터 선별, 재학습, 성능 검증 평가, 신구 비교, 배포 패키지 생성까지의 전 과정을 하나의 흐름으로 작동시키는 데 집중합니다.

시연 데이터는 공개 산업용 이상탐지 데이터셋인 VisA(Visual Anomaly, Amazon Science, CC BY 4.0)를 사용하며 출처와 라이선스를 명시합니다. 사내 데이터는 일절 사용하지 않습니다. VisA를 선택한 이유는 세 가지입니다. 첫째, 객체별로 여러 결함 유형이 라벨링되어 있어 특정 유형만 학습에서 제외하는 조작이 정확히 가능합니다. 둘째, 픽셀 단위 마스크가 제공되어 결함 면적을 계산할 수 있으므로 판정 기준 테이블을 실제로 구성할 수 있습니다. 셋째, 상업적 이용이 허용되는 라이선스라 대회 참가에 제약이 없습니다.

가상 공장은 공개 데이터셋을 그대로 쓰는 것이 아니라 실제 라인 운영을 본떠 구성했습니다. 서로 형상이 다른 네 품목을 각각 별개의 생산 라인으로 두고, 로트 40개를 로트당 100장으로 나누어 전체 4,039장을 구성합니다. 로트 하나는 정상 90장과 결함 10장으로 채웁니다. 품목마다 메모리 뱅크를 따로 가져가는데, 같은 계열이라도 정상 패치가 달라 하나의 뱅크로 판정할 수 없습니다. 근거는 3-5절에 있습니다.

**[표 4-1] 아직 검사하지 않은 생산분을 따로 둔다**
| 구간 | 로트 | 이미지 | 결함 비율 | 역할 |
|---|---|---|---|---|
| bank | 12 | 1,200장 | 0% | 초기 메모리 뱅크 구성 재료 |
| operation | 16 | 1,631장 | 11.7% | 운영 구간 — 미검출이 발생하는 곳 |
| holdout | 8 | 808장 | 10.9% | 성능 검증이 성능을 재는 구간 |
| pending | 4 | 400장 | 10.0% | 아직 검사하지 않은 생산분 |

pending 구간이 예약 스케줄러가 점검하는 대상입니다. 이 구간이 있어야 신구 비교가 정답 라벨이 없는 양산 데이터를 다루는 실제 상황이 됩니다. 아직 판정되지 않은 데이터에 신구 뱅크를 병렬로 돌리고 갈린 건만 추려내는 일이 실제 운영에서 벌어집니다.

로트 크기를 줄인 데에도 근거를 뒀습니다. 처음에는 로트를 1,000장으로 잡았는데, 공개 데이터셋은 카테고리당 결함이 100장뿐입니다. 로트가 크면 같은 원본을 여러 번 재사용하게 됩니다. 홀드아웃에서 같은 이미지를 두 번 세면 성능 검증 점수가 부풀려집니다. 로트 1,000장 시절에는 결함 원본 하나가 평균 아홉 번 재사용되었고, 100장으로 줄인 지금은 평균 1.5회입니다.

메모리 뱅크는 구성 후보 전부가 아니라 정상 150장으로 세웁니다. coreset 선별은 후보 수에 비례해 비용이 늘어, 전부를 넣으면 끝나지 않습니다. 혼입률도 이 분모로 재야 맞습니다. 후보 전체를 분모로 잡으면 혼입 비율이 실제의 절반으로 옅어 보입니다.

이 구조 위에 아래 표와 같이 이슈 유형별 시나리오를 구성합니다. 총 24건이며 모든 시나리오는 정답 원인이 사전에 확정되어 있어 진단 정확도를 실제로 측정할 수 있습니다.

**[표 4-2] 24건 가운데 19건은 현장 근거, 5건은 기술적 가정**
| 이슈 유형 | 정답 원인 | 시연 데이터 구성 방법 | 건수 | 근거 |

24건 가운데 19건은 현장에서 실제로 겪은 상황에 근거하며, 5건은 기술적 가정입니다. 가정에 해당하는 것은 설비·광학 4건 전부와 기준 문제 1건입니다. 팀의 현장 경험이 정상품을 불량으로 판정하는 과검 방향에 치우쳐 있는 반면 이 과제는 불량을 정상으로 판정하는 미검을 다루기 때문이며, 해당 5건은 시나리오 파일 안에 명시적으로 표시해 두었습니다. 시연과 발표는 현장 근거 19건을 중심으로 구성하고, 가정 5건은 본선 기간에 도메인 검토를 거쳐 보완합니다.

이 가운데 뱅크 오염 시나리오가 가장 중요합니다. 정상 학습 데이터에 불량이 섞이면 유사한 불량이 전부 정상으로 판정되는데, 현업에서 원인 규명이 가장 오래 걸리는 유형이면서 동시에 최근접 패치 역추적으로 즉시 밝혀지는 유형이기 때문입니다. 에이전트를 두는 이유가 가장 선명하게 드러나는 케이스이므로 시연의 중심에 둡니다.

### 4-3. 기술 스택과 개발 환경, 개발 방법론

**개발 환경**
개발과 시연 모두 RTX 4090을 탑재한 노트북 한 대에서 수행합니다. 현장에 그대로 들고 갈 수 있어 개발 환경과 시연 환경이 동일하며, 환경 차이로 인한 시연 사고 가능성이 없습니다. 별도의 클라우드 GPU는 사용하지 않습니다.

데이터는 전부 공개 데이터셋과 가상 생성분이므로 사내망 연결이나 사내 데이터 반입이 없습니다. 언어 모델과 시각 언어 모델은 단일 GPU에서 구동 가능한 공개 모델을 우선 검토하며, 모델 호출은 어댑터 계층 뒤에 두어 설정만으로 교체할 수 있게 했습니다. 실환경의 폐쇄망 적용을 전제로 한 설계이며, 최종 통합 테스트는 외부 통신을 차단한 상태에서 수행해 이를 확인합니다.

협업은 Git 저장소로 진행합니다. 대용량 원본과 메모리 뱅크는 저장소에 넣지 않고 생성 스크립트로 재현하며, 시드를 고정해 세 사람이 동일한 데이터 구조를 만들 수 있도록 했습니다.

**기술 스택과 개발 방법론**
프로토타입은 Python 기반 웹 애플리케이션으로 개발합니다. 에이전트 계층은 언어 모델과 시각 언어 모델을 도구 호출 방식으로 구성하며, 시연에는 단일 GPU에서 구동 가능한 공개 비전 언어 모델을 사용합니다. 모델 호출은 어댑터 계층 뒤에 두어 설정만으로 교체할 수 있게 했고, 각 에이전트가 판단 결과와 근거를 구조화된 형태로 다음 단계에 전달하도록 설계합니다. 이상탐지 모델은 현행 검사 시스템과 동일한 PatchCore를 사용하며, 품목마다 별도의 메모리 뱅크를 유지합니다. 정상 패치의 메모리 뱅크와 최근접 거리 기반 판정이라는 구조가 동일해야 시연 결과를 실환경 적용 논의로 이어갈 수 있기 때문입니다. PatchCore는 역전파 학습이 없어 뱅크 재구성이 수 분 내에 완료되므로, 단일 GPU 환경에서 개선 루프를 반복 실행하며 검증하기에도 유리합니다. 모델 자체는 공개 구현을 사용하며, 이번 과제에서 새로 만드는 것은 최근접 패치 역추적을 활용한 진단 로직과 평가 판단 로직입니다.

현장이 쓰는 말과 데이터가 쓰는 값이 다르다는 점도 접수 단계에서 흡수합니다. 이슈는 한국어 자연어로 오지만 조회와 대조는 정확한 문자열 일치로 이루어지므로, 라인 표기와 결함 유형을 공개 데이터셋의 어휘로 맞춘 뒤 다음 단계로 넘깁니다. 어휘표는 데이터셋의 라벨에서 생성하며 코드에 따로 적지 않습니다. 맞출 수 없는 표현은 추측해서 채우지 않고 되묻습니다. 이 단계가 없으면 유사 사례 검색이 조용히 빈손이 되어, 이미 처리한 문제가 새 이슈로 다시 접수됩니다.

지식·데이터 계층은 두 종류로 나뉩니다. 뱅크 구성 프로파일, 화질 기준 분포, 임계값, 판정 기준은 정확한 값이 필요하므로 관계형 테이블과 조회 함수로 구현합니다. 반면 과거 이슈와 진단 원인, 조치 결과를 연결한 이력은 유사 사례 탐색이 목적이므로 그래프 구조로 정의하고 검색을 붙입니다. 진단의 판정 근거는 전자에서 나오고, 후자는 중복 작업을 막는 보조 역할을 합니다.

어느 방식이 나은지는 단정하지 않고 측정해서 정합니다. 조회 계층 전체를 LookupLayer라는 단일 인터페이스 뒤에 두었기 때문에, 동일한 24건 시나리오에 그래프 기반 검색 구현을 끼워 넣으면 진단 코드를 한 줄도 고치지 않고 두 방식의 진단 정확도를 비교할 수 있습니다. 결과가 비슷하거나 나으면 채택하고, 나쁘면 그 수치 자체가 왜 채택하지 않았는지에 대한 답이 됩니다. 어느 쪽이 나오든 근거가 남는다는 점에서 이 비교를 본선 과제에 포함했습니다. 전 구간 실행에서 호출된 조회는 대부분이 조인이고 그래프 검색은 과거 이슈 이력 하나뿐이며 역할은 중복 차단입니다. 전부를 검색으로 찾는 구조가 아니라는 점, 그리고 진단의 근거가 결정론적 조회에서 나온다는 구분이 실행에서 그대로 확인되었습니다. 그래프 스키마는 문서로 정의하여, 이후 실플랫폼으로 옮길 때 스키마가 그대로 유지되도록 합니다.

모델 버전과 평가 이력은 데이터베이스로 관리하고, 예약 작업은 스케줄러가 처리합니다. 에이전트는 작업을 등록한 뒤 종료되고 지정된 시각에 스케줄러가 다시 호출하는 구조로 설계하여, 장시간 대기 상태를 두지 않습니다.

개발은 2주 스프린트로 진행하며, 본선 기간에 제공되는 Claude Max와 Vibe Coding 교육을 활용해 구현 속도를 확보합니다. 기능별 모듈화와 실행 환경 문서화를 통해 코드 품질과 재현성을 관리합니다. 향후 실환경 적용을 고려하여 외부 통신 없이 폐쇄망에서 동작할 수 있는 구조를 전제로 설계합니다.

### 5-2. 개발 일정

**예선 기간의 사전 작업**
설계의 타당성을 검증하기 위해 핵심 판정 로직을 구현했습니다. 3-5절의 실측 결과는 그 과정에서 얻은 것입니다. 현재 동작하는 것은 다음과 같습니다.
- PatchCore 추론, 최근접 패치 역추적, 임계값 스윕
- 언어 모델과 시각 언어 모델의 어댑터 계층
- 이슈 접수·진단·데이터 선별 에이전트
- 뱅크 재구성, 성능 검증, 신구 비교, 승인 요청 생성
- 이슈 접수 웹 화면과 도구 호출 경로
- 가상 공장 데이터 생성기와 조회 계층, 이슈 이력 그래프
- 예약 실행 스케줄러와 학습 이력 인덱서
- 라인·품목별 뱅크 저장소와 되돌리기

테스트는 435건 가운데 430건을 통과하고 5건을 건너뛰었습니다. 실제 언어 모델로 전 구간이 순서대로 실행되는 것도 확인했습니다.

**남은 과제**
남은 것은 셋입니다.
- **판별 1번의 위치 추정** — 정확한 위치를 주면 판독이 잘 되지만 기판 계열에서 이상 히트맵이 자리를 짚지 못합니다. 원인 후보를 좁힌 결과 남은 것이 특징 추출기 교체입니다.
- **판별 7번 면적의 컷오프 값** — 계산 방식은 고쳤고 값을 재는 일이 남았습니다.
- **결함이 눈에 보이지 않는 경우의 분류 기준** — 현재 규칙은 판정을 보류합니다. 정상 분포 중첩에서 이 보류가 옳은지 도메인 판단이 필요합니다.

**본선 1주 차**
이 셋을 마무리합니다. 에이전트 담당이 특징 추출기 교체가 위치 추정 병목에 닿는지를 검증하고, 실제 모델을 통과한 진단 정확도를 측정합니다. 도메인 담당이 면적 컷오프와 성능 검증 통과 기준값을 확정하고, 결함이 확인되지 않는 경우의 분류 기준을 정합니다. 데이터 담당이 조회 계층의 규모 대응과 결과 표기를 정비하고 예약 실행 경로의 안정성을 확인합니다. 1주 차 완료 기준은 실제 모델 기준의 진단 정확도가 재측정되는 것입니다.

**본선 2주 차**
조회 계층의 두 구현을 동일 시나리오로 비교해 4-3절에서 언급한 결과를 확보하고, 거버넌스 기록 스키마와 업무 표준 절차를 정리합니다. 이어서 3인이 함께 전 구간을 반복 실행해 통합 테스트와 재현성 검증을 수행하며, 최종 통합 테스트는 외부 통신을 차단한 상태에서 수행하여 폐쇄망 동작 가능성을 함께 확인합니다. 설명서와 시연 영상, 발표자료를 준비합니다. 2주 차 완료 기준은 전 구간이 무중단으로 완주하고 10회 반복 시 동일한 성능 검증 판정이 나오는 것입니다.

**결선**
시연 안정성을 높이고, 남은 판별 경계의 정확도를 개선하며, 예약 실행 시나리오를 포함한 확장 시연과 피칭 자료를 완성합니다.

### 5-3. 리스크 및 대응 방안
사내 데이터 사용 제약은 가장 확실한 리스크입니다. 프로토타입 전 과정을 공개 데이터셋 기반으로 구성하여 원천적으로 회피하고, 사내 데이터는 일절 반입하지 않으며 기획서와 산출물에도 공정 조건, 장비 공급사, 생산 거점, 사내 결함 정의 체계 등 식별 가능한 정보를 포함하지 않습니다. 학습 이력 인덱서 역시 사내 폴더 구조를 전제하지 않고 일반적인 스캔 규칙으로 추상화해 구현합니다.

시각 언어 모델의 판독은 관심 영역을 정확히 지정해야 신뢰할 수 있는데, 표 2-2에서 보듯 품목에 따라 이상 히트맵이 결함 자리를 짚지 못하는 경우가 있습니다. 남은 후보인 특징 추출기 교체로 대응하되, 개선되지 않으면 해당 품목에서는 판독을 보조 근거로만 사용하고 조회와 계산 기반 항목의 비중을 높입니다. 판별 항목이 일곱 개이고 하나가 빠져도 나머지로 판정이 성립하도록 설계한 것이 이 상황에 대한 대비입니다. 진단 에이전트의 오판 가능성은 서비스 신뢰도와 직결됩니다. 판단 근거를 반드시 함께 제시하도록 하고, 확신도가 낮으면 자동 진행 대신 사람에게 확인을 요청하는 경로를 둡니다. 또한 원인 분류가 틀리더라도 이후의 성능 검증에서 걸러지도록 이중 안전장치를 둡니다.

과거 학습 이력의 역추정 결과가 사실과 다를 위험이 있습니다. 역추정된 항목은 반드시 추정으로 표시하고 근거가 되는 뱅크 구성 차이를 함께 남기며, 담당자가 확인한 경우에만 확정 이력으로 승격하는 절차를 둡니다. 추정을 기록처럼 취급하지 않는 것이 원칙입니다.

자동으로 실행되는 경로가 늘어날수록 조용히 틀리는 답이 가장 위험합니다. 조회 계층의 건수 상한 때문에 데이터가 잘려 나가면서 결함이 전부 빠진 채 미검출이 없다는 답이 나온 사례가 있었고, 오류가 아니라 정상 응답으로 나오기 때문에 발견이 늦습니다. 상한에 닿았다는 사실을 결과에 함께 적도록 바꾸었고, 실제 운영 규모의 데이터를 시험에 포함시켜 규모 때문에 갈리는 문제를 개발 단계에서 잡도록 했습니다.

2주라는 짧은 개발 기간에 따른 범위 확대 위험은, 뱅크 오염 시나리오 한 건의 완결된 루프를 우선 완성한 뒤 나머지 원인 유형으로 확장하는 방식으로 관리합니다. 여러 기능을 얕게 만드는 대신 하나의 시나리오가 끝까지 작동하는 것을 우선순위로 둡니다.

신구 비교에서 판정 불일치 건수가 지나치게 많아 사람 확인 부담이 커질 가능성에 대해서는, 불일치 케이스를 신뢰도 순으로 정렬해 상위 일부만 확인하는 방식과 표본 추출 방식을 함께 준비합니다.

실환경 적용 시에는 검사 장비 공급사 플랫폼에 외부 제어 인터페이스가 없을 수 있다는 제약이 있습니다. 이에 대해 서비스는 배포 패키지 생성까지를 자동화 범위로 명확히 한정하고, 실제 장비 반영은 담당자 승인과 수동 적용을 전제로 설계했습니다. 또한 폐쇄망 환경에서 외부 통신 없이 동작해야 하므로 언어 모델과 시각 언어 모델의 온프레미스 실행을 전제로 설계하며, 자원 제약에 따라 경량 모델 적용이나 진단 계층의 서버 분리를 선택할 수 있도록 모듈을 분리합니다.

## 6. 기대효과

### 6-1. 활용 분야
일차적으로는 배터리 제조 공정의 외관검사 AI 운영에 적용합니다. 현행 검사 시스템과 동일한 PatchCore 기반으로 설계했으므로 시연 결과를 그대로 실환경 적용 논의로 이어갈 수 있으며, 특정 라인의 단일 검사 영역에서 시작해 동일 공정의 다른 검사 영역으로 확대할 수 있습니다.

나아가 검사 대상이 무엇이든 미검출 발생, 원인 진단, 데이터 확보, 재학습, 검증, 배포로 이어지는 루프는 동일합니다. 따라서 반도체, 디스플레이, 소재, 화학 등 비전 기반 검사 설비를 운영하는 모든 제조 현장에 같은 구조를 적용할 수 있습니다. 검사 영역뿐 아니라 예지보전, 공정 이상 감지 등 현장에 배포된 다른 AI 모델의 운영에도 확장 가능합니다.

### 6-2. 기대 효과
이 과제가 추구하는 SUPEX는 사람을 줄이는 것이 아니라 사람이 감당하는 총량의 상한을 없애는 데 있습니다. 지금은 대응 가능한 검출력 이슈의 수가 담당 인력 수에 그대로 묶여 있어, 검사 AI를 확대 적용할수록 밀리는 이슈가 늘어납니다. 개선 루프에서 사람이 판단해야 하는 지점을 승인 한 곳으로 좁히면 그 상한이 풀립니다.

정량적으로는 검출력 이슈 하나의 리드타임이 수 주 단위에서 일 단위로 단축되는 것을 목표로 합니다. 표 1에서 확인했듯 이 단축분의 대부분은 작업 속도 개선이 아니라 대기 구간 제거에서 나오므로, 담당자의 업무 강도를 높이지 않고도 달성 가능하다는 점이 중요합니다.

같은 인원이 대응할 수 있는 이슈 건수가 늘어나면서, 그동안 우선순위에 밀려 처리되지 못했던 이슈까지 소화할 수 있게 됩니다. 검사 AI 적용 범위 확대가 담당 인력 증원에 종속되지 않는다는 점이 가장 큰 효과입니다.

검증 부담도 줄어듭니다. 14장을 신구 뱅크에 병렬로 돌렸을 때 판정이 갈린 것은 한 장이었고, 사람이 확인할 대상도 그 한 장이었습니다. 정답 라벨이 없는 양산 데이터에서 뱅크 교체의 영향을 재면서 확인 공수는 줄인 셈입니다. 임계값 조정만으로 해결될 사안을 재학습으로 처리하던 경우가 걸러지므로, 대응 공수 자체도 줄어듭니다.

정성적으로는 지식 자산화 효과가 가장 큽니다. 그동안 숙련자의 경험과 기억에 머물러 있던 원인 진단 기준, 검증 기준, 그리고 재학습 의도가 명시적인 기록으로 남습니다. 담당자가 바뀌어도 모델이 무엇을 학습했고 왜 그렇게 판단했는지를 후임자가 그대로 이어받을 수 있으며, 거점이 늘어나도 동일한 수준의 운영이 유지됩니다. 신규 담당자도 에이전트의 판단 근거를 따라가며 빠르게 숙련될 수 있습니다.

### 6-3. 서비스 확장 계획
단기적으로는 하나의 검사 영역을 대상으로 파일럿을 수행하여 진단 정확도와 리드타임 개선 효과를 검증하고, 현장 담당자 피드백으로 판정 기준을 보정합니다. 동시에 학습 이력 인덱서로 기존 프로젝트 폴더를 스캔해 과거 이력을 자산화합니다.

중기적으로는 동일 공정의 다른 검사 영역과 다른 생산 거점으로 확대하고, PatchCore 외의 검사 알고리즘에도 동일한 진단 체계를 적용할 수 있도록 판별 항목을 일반화하며, 거점 간 개선 이력을 통합해 한 곳에서 해결된 문제를 다른 곳이 재사용할 수 있도록 합니다. 서로 다른 장비 공급사 환경을 함께 수용하는 벤더 중립 레지스트리를 완성합니다.

장기적으로는 제조 현장에 배포된 AI 모델 전반의 운영을 관장하는 표준 플랫폼으로 발전시킵니다. 검사 AI를 넘어 예지보전과 공정 이상 감지 모델까지 동일한 운영 루프에 편입시키고, SK그룹 내 제조 멤버사가 공통으로 활용할 수 있는 형태로 확장하는 것을 목표로 합니다.
