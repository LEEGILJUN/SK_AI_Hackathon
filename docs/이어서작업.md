## 1. 환경 준비 (처음 한 번)

```bash
git clone https://github.com/LEEGILJUN/SK_AI_Hackathon.git
cd SK_AI_Hackathon
```

파이썬 환경은 venv 든 conda 든 상관없습니다. **4090 노트북(Windows)에는 conda
환경 `Hackathon` 으로 이미 만들어 두었습니다.**

| 환경 | 파이썬 실행 경로 |
|---|---|
| Mac · Linux (venv) | `.venv/bin/python` |
| Windows (venv) | `.venv\Scripts\python.exe` |
| **Windows 4090 (conda, 현재 사용 중)** | `%LOCALAPPDATA%\anaconda3\envs\Hackathon\python.exe` |

**이 문서와 `CLAUDE.md` 의 `.venv/bin/python` 은 Mac 기준 표기입니다.**
Windows 에서는 위 표의 경로로 바꿔 읽으세요.

```bash
pip install -r requirements.txt
python -m pytest tests/ -q          # 165건 통과해야 정상
```

**torch 는 Windows 에서 CPU 판이 깔립니다.** `requirements.txt` 위쪽 주석대로
cu126 인덱스에서 다시 설치해야 GPU 를 씁니다. 확인은 이렇게 합니다.

```bash
python -c "import torch; print(torch.__version__, torch.cuda.is_available())"
# 2.13.0+cu126 True  가 나와야 합니다
```

백본 가중치는 처음 한 번 내려받아야 합니다 (약 130MB).

```bash
python -c "from torchvision.models import get_model; get_model('wide_resnet50_2', weights='IMAGENET1K_V1')"
```

VisA 는 1.80 GB 입니다. `.gitignore` 가 `VisA_*/` 와 `*.tar` 를 잡고 있어
저장소 안에 풀어도 커밋되지 않습니다. 다만 **커밋 전에 `git status` 로 한 번
확인하세요** — 한 번 커밋될 뻔했습니다.

```bash
curl -O https://amazon-visual-anomaly.s3.amazonaws.com/VisA_20220922.tar
```

사내망에서 `curl: (35) ... 0x80092012` 가 나면 인증서 폐기목록(CRL) 조회가
막힌 것입니다. 인증서 검증은 그대로 두고 폐기 조회만 건너뜁니다.

```bash
curl -L --ssl-no-revoke -C - -O https://amazon-visual-anomaly.s3.amazonaws.com/VisA_20220922.tar
```

풀면 카테고리 12개가 나옵니다. capsules 기준 정상 602장 · 결함 100장입니다.

장치는 자동으로 잡힙니다. Mac 에서는 mps, 4090 에서는 cuda 로 갑니다
(`inspection/device.py`). 코드를 고칠 필요 없습니다.

## 3. 지금 바로 할 일

### 1번 — 모델 붙이고 도구 호출이 되는지 확인

**4090 노트북에는 Ollama 와 모델이 이미 깔려 있습니다.** 새로 받을 필요가
없습니다. GGUF 원본과 Modelfile 이 별도 경로에 있고 `ollama list` 의 12개가
그 파일들을 가리킵니다.

| 용도 | 후보 | 크기 | 고른 근거 |
|---|---|---|---|
| LLM | `qwen3-14b` | 9.0 GB | Modelfile 에 Qwen 표준 `<tool_call>` 템플릿과 `.Tools` 렌더링이 있음 |
| VLM | `qwen3vl-8b` | 6.2 GB | mmproj 동봉, `temperature 0.1` |

둘을 함께 올리면 15.2 GB 로 16 GB 안에 들어갑니다.

**`gemma4-31b` · `gemma4-26b` 는 Modelfile 에 `.Tools` 처리가 없습니다.**
도구 호출 검사를 통과하지 못할 가능성이 큽니다. 예선 기획 시점에는 Gemma 4 를
전제했지만 이 장비의 실물 기준으로는 qwen3 계열이 먼저입니다.
**다만 이건 Modelfile 을 읽고 추정한 것이고 아직 측정하지 않았습니다.**
아래를 돌려 실제로 갈라야 합니다.

```powershell
$env:SHVO_LLM_PROVIDER = "openai_compat"
$env:SHVO_LLM_BASE_URL = "http://localhost:11434/v1"
$env:SHVO_LLM_MODEL    = "qwen3-14b"
$env:SHVO_VLM_PROVIDER = "openai_compat"
$env:SHVO_VLM_BASE_URL = "http://localhost:11434/v1"
$env:SHVO_VLM_MODEL    = "qwen3vl-8b"

python scripts/check_models.py
```

Mac · Linux 면 `export SHVO_LLM_PROVIDER=openai_compat` 형식으로 씁니다.

어댑터 코드(`agents/adapters/openai_compat.py`)는 **이미 구현돼 있습니다.**
미연결의 원인은 코드가 없어서가 아니라 `SHVO_*_PROVIDER` 기본값이 `stub` 이기
때문입니다. 환경 변수만 맞으면 붙습니다.

이 스크립트가 네 가지를 각각 실제로 시켜 봅니다.

| 검사 | 왜 보는가 |
|---|---|
| 응답 | 살아 있는가 |
| JSON 출력 | 진단 근거가 전부 이 형식으로 오간다 |
| **도구 호출** | 에이전트 오케스트레이션의 전제. 서버·모델 조합마다 되고 안 되고가 갈린다 |
| 이미지 판독 | 판별 1·5번이 여기 걸려 있다 |

**도구 호출이 안 되면 모델을 바꿔야 합니다.** 2번을 해도 소용이 없습니다.

이미지 판독 검사는 합성 결함/정상을 구분하는지만 봅니다. 사람 눈에도 명확한
이미지라 통과해도 실전 보장은 안 됩니다. VisA 실데이터로 다시 재야 합니다.

### 2번 — 웹 데모를 도구 호출 경로로 바꾸기

지금 `app/pipeline.py` 는 이렇게 순서대로 부릅니다.

```python
intake = receive(...)
result = score_image(...)
diagnosis = decide(...)
plan = plan_curation(...)
rebuild = execute_rebuild(...)
```

이걸 `agents/tools.py` 의 `ToolRegistry` + `run_agent` 경로로 바꿔야 합니다.
도구 명세(`DIAGNOSE_SPEC`, `PLAN_SPEC`, `REBUILD_SPEC`, `COMPARE_SPEC`)와
루프는 이미 있고 테스트도 통과합니다. **연결만 안 돼 있습니다.**

바꿀 때 지켜야 할 것:

- **언어 모델이 원인을 정하면 안 됩니다.** 모델은 "어떤 도구를 어떤 순서로
  부를지"만 정하고, 판정 내용은 `decide()` 가 규칙으로 냅니다. 이 분리가
  깨지면 진단이 인상 평가가 됩니다.
- 큐레이션이 막은 계획은 재구성 도구가 거부해야 합니다. 모델이 재구성을
  불러도 실행되면 안 됩니다. 지금 `tests/test_tools.py` 에 이 테스트가 있습니다.
- 배포하는 도구는 만들지 않습니다.

## 4. 알아 둬야 할 결정들

이유를 모르면 되돌리기 쉬운 것들입니다.

**입력 해상도 512/448 을 낮추지 마세요** (`inspection/features.py`).
흔히 쓰는 256/224 로는 VisA 결함을 거의 못 잡습니다. 결함이 원본에서
40×40px 라 격자 한 칸에 묻히고 이웃 평균에 희석됩니다.

| 설정 | AUROC | 측정 조건 |
|---|---|---|
| 256/224, 정상 60장 | 0.526 (무작위 수준) | 홀드아웃 정상 25 / 결함 25 |
| 512/448, 정상 60장 | 0.931 | 홀드아웃 정상 25 / 결함 25 |
| 256/224, 정상 150장 | 0.502 | 홀드아웃 정상 25 / 결함 25 |
| 512/448, 정상 150장 | 0.998 | 홀드아웃 정상 25 / 결함 25 |
| 512/448, 정상 225장 | 0.941 | 홀드아웃 정상 75 / 결함 12 |

**AUROC 는 홀드아웃 구성이 다르면 직접 비교할 수 없다.** 위 표에서 150장의
0.998 과 225장의 0.941 을 나란히 놓고 "데이터를 늘렸더니 나빠졌다"로 읽으면
안 된다. 앞의 넷은 같은 홀드아웃(25/25)에서 해상도와 뱅크 크기만 바꾼 것이고,
마지막 줄은 홀드아웃이 75/12 로 달라 양품이 3배다. 과검 한 건의 무게가 다르다.

데이터를 더 넣어도 해상도가 모자라면 신호 자체가 없습니다.

**coreset 이 오염을 증폭합니다.** 서로 먼 점을 우선 남기는 방식이라 결함
패치가 먼저 선택됩니다. 원본의 12.5% 였던 오염원이 비율 0.25 에서 뱅크의
50%, 0.1 에서 70% 를 차지했습니다. `contamination_amplification()` 으로
확인할 수 있습니다.

**임계값 스윕은 "왜 안 되는지"를 말해주지 못합니다.** VisA 실측에서 오염된
뱅크는 "임계값 조정으로 해결 불가"로 나왔습니다(AUROC 0.883, 전건 검출에
과검률 59.5%). 여기까지는 잘 작동합니다. 문제는 **정상 분포 중첩에서도 똑같이
"해결 불가"가 나온다**는 것입니다. 두 원인은 조치가 정반대입니다 — 오염은
제거 후 재구성, 중첩은 재구성 금지. 스윕은 그 갈림을 만들지 못하고 역추적이
만듭니다. 그래서 진단이 **역추적을 임계값보다 먼저** 봅니다.

합성 데이터에서는 오염된 뱅크도 AUROC 1.000 에 "해결 가능"이 나왔습니다.
결함이 지나치게 뚜렷해 상대 순서가 유지된 탓이며 **실데이터에서는 재현되지
않습니다.** 합성 결과를 근거로 삼지 마세요.

**greedy coreset 은 O(k·N)** 이라 실데이터에서 비율을 크게 잡으면 끝나지
않습니다. `build_bank(max_bank_size=...)` 상한이 걸려 있고, 걸리면 meta 에
남습니다.

**`inspect` 는 파이썬 표준 라이브러리 이름**이라 패키지로 못 씁니다.
그래서 `inspection` 입니다.

## 5. 건드리면 안 되는 것

- **`data/scenarios.yaml`** — 장영진 소유의 정답 파일. 진단 정확도를 맞추려고
  고치지 않습니다. 변경은 합의 후.
- **배포 기능을 만들지 않습니다.** `agents/release.py` 는 배포 패키지와 승인
  요청 문서까지만 만듭니다. `deploy`/`apply`/`install` 이름의 함수가 생기면
  `tests/test_gate_release.py` 가 실패합니다. 의도적인 장치입니다.
- **VisA 원본과 뱅크 파일을 커밋하지 않습니다.** `.gitignore` 에 있습니다.
- **사내 데이터를 넣지 않습니다.** 공정 조건, 장비 공급사, 생산 거점, 사내
  결함 정의는 코드·주석·문서 어디에도.
