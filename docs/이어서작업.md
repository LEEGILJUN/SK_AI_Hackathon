## 1. 환경 준비 (처음 한 번)

```bash
git clone https://github.com/LEEGILJUN/SK_AI_Hackathon.git
cd SK_AI_Hackathon
```

파이썬 환경은 venv 든 conda 든 상관없습니다. **4090 노트북(Windows)에는 conda
환경 `Hackathon` 으로 이미 만들어 두었습니다.**

| 환경 | 파이썬 실행 경로 |
|---|---|
| Mac · Linux (venv) | `.venv/bin/python` |
| Windows (venv) | `.venv\Scripts\python.exe` |
| **Windows 4090 (conda, 현재 사용 중)** | `%LOCALAPPDATA%\anaconda3\envs\Hackathon\python.exe` |

**이 문서와 `CLAUDE.md` 의 `.venv/bin/python` 은 Mac 기준 표기입니다.**
Windows 에서는 위 표의 경로로 바꿔 읽으세요.

```bash
pip install -r requirements.txt
python -m pytest tests/ -q          # 285건 통과해야 정상
```

**torch 는 Windows 에서 CPU 판이 깔립니다.** `requirements.txt` 위쪽 주석대로
cu126 인덱스에서 다시 설치해야 GPU 를 씁니다. 확인은 이렇게 합니다.

```bash
python -c "import torch; print(torch.__version__, torch.cuda.is_available())"
# 2.13.0+cu126 True  가 나와야 합니다
```

백본 가중치는 처음 한 번 내려받아야 합니다 (약 130MB).

```bash
python -c "from torchvision.models import get_model; get_model('wide_resnet50_2', weights='IMAGENET1K_V1')"
```

VisA 는 1.80 GB 입니다. `.gitignore` 가 `VisA_*/` 와 `*.tar` 를 잡고 있어
저장소 안에 풀어도 커밋되지 않습니다. 다만 **커밋 전에 `git status` 로 한 번
확인하세요** — 한 번 커밋될 뻔했습니다.

```bash
curl -O https://amazon-visual-anomaly.s3.amazonaws.com/VisA_20220922.tar
```

사내망에서 `curl: (35) ... 0x80092012` 가 나면 인증서 폐기목록(CRL) 조회가
막힌 것입니다. 인증서 검증은 그대로 두고 폐기 조회만 건너뜁니다.

```bash
curl -L --ssl-no-revoke -C - -O https://amazon-visual-anomaly.s3.amazonaws.com/VisA_20220922.tar
```

풀면 카테고리 12개가 나옵니다. capsules 기준 정상 602장 · 결함 100장입니다.

장치는 자동으로 잡힙니다. Mac 에서는 mps, 4090 에서는 cuda 로 갑니다
(`inspection/device.py`). 코드를 고칠 필요 없습니다.

### 4090 에서는 `git fetch` 가 조용히 실패합니다 — 해시로 확인하세요

**이것 때문에 한 번 크게 헛짚었습니다.** 4090 이 `origin/main` 최상단을
`1c7df36` 으로 읽고 "푸시가 안 된 것 같다 · 테스트 개수가 한참 모자란다 ·
`main` 의 `app/view.py` 가 3.11 에서 안 뜬다"를 보고했는데 **셋 다 틀렸습니다.**
실제로는 10커밋 뒤처져 있었습니다. `fetch` 가 `Empty reply from server` 로
여러 번 끊겼고, 재시도 중 한 번 성공한 것을 완료로 읽은 것입니다.

`git push` 만 막힌 게 아니라 **읽는 쪽도 불안정합니다.** 종료 코드나 부분
성공을 최신 상태의 근거로 쓰지 마세요.

```bash
git fetch origin && git rev-parse origin/main
# 기대하는 해시와 눈으로 대조합니다. 다르면 fetch 를 다시 합니다
```

**측정 기계가 낡은 코드를 재면 결과가 통째로 무의미해집니다.** 4090 에
실험을 넘길 때는 기대 HEAD 해시를 함께 주고, 받는 쪽은 그것부터 맞춥니다.

### 테스트가 4090 에서 49초인 것은 정상입니다

맥은 8~10초인데 4090 은 49.4초입니다. **회귀가 아니라 torch import + CUDA
초기화 비용**이고 맥은 mps 라 그 비용이 없습니다.

다만 **시간으로 판별하지 마세요.** 예전에 VisA 자동 감지가 테스트 픽스처를
물어 8초가 11분 29초가 된 적이 있는데, 그때 확인해야 할 것은 걸린 시간이
아니라 `DemoFactory` 가 어느 경로로 섰는가였습니다. 픽스처가
`visa_root=.../_no_visa_here` 를 물고 있는지 직접 보면 됩니다.

| 256/224, 정상 60장 | 0.526 (무작위 수준) | 홀드아웃 정상 25 / 결함 25 |
| 512/448, 정상 60장 | 0.931 | 홀드아웃 정상 25 / 결함 25 |
| 256/224, 정상 150장 | 0.502 | 홀드아웃 정상 25 / 결함 25 |
| 512/448, 정상 150장 | 0.998 | 홀드아웃 정상 25 / 결함 25 |
| 512/448, 정상 225장 | 0.941 | 홀드아웃 정상 75 / 결함 12 |

**AUROC 는 홀드아웃 구성이 다르면 직접 비교할 수 없다.** 위 표에서 150장의
0.998 과 225장의 0.941 을 나란히 놓고 "데이터를 늘렸더니 나빠졌다"로 읽으면
안 된다. 앞의 넷은 같은 홀드아웃(25/25)에서 해상도와 뱅크 크기만 바꾼 것이고,
마지막 줄은 홀드아웃이 75/12 로 달라 양품이 3배다. 과검 한 건의 무게가 다르다.

데이터를 더 넣어도 해상도가 모자라면 신호 자체가 없습니다.

**기판에서도 512 로 충분합니다 — 오히려 캡슐보다 낫습니다.**
시나리오 24건이 pcb 로 짜여 있는데 실측은 capsules 뿐이라 구멍이었습니다.
2026-08-14 에 4090 이 닫았습니다(`scripts/measure_auroc.py`).

| 카테고리 | AUROC | 겹침 |
|---|---|---|
| pcb1 | 1.000 | 없음 |
| pcb2 | 0.998 | 있음 |
| pcb3 | 1.000 | 없음 |
| pcb4 | 1.000 | 없음 |
| capsules | 0.989 | 있음 |

같은 조건입니다 — 512/448 · 뱅크 정상 150 · 홀드아웃 25/25 · 오염 0.
**"기판은 배경이 절반 이상이고 결함이 더 작으니 512 가 모자랄 것"이라는 우려가
재현되지 않았습니다.**

여기 capsules 가 0.989 인데 위 표의 0.998 과 다릅니다. 파라미터는 같고
**원 측정이 어느 25장을 홀드아웃으로 썼는지 기록이 없어서**입니다.
`measure_auroc.py` 는 분할을 독스트링에 못박았으니 다음부터는 재현됩니다.

**교차 측정이 더 셉니다.** pcb1(HC-SR04 앞면) 뱅크로 재면 —

```
pcb1 정상 (앞면)   1.708 ~ 2.104
pcb1 결함          3.172 (중앙)
pcb2 정상 (뒷면)   3.421 ~ 3.643    ← AUROC 1.000, 겹침 없음
```

**뒷면의 멀쩡한 기판이 앞면의 진짜 결함보다 높게 찍힙니다.** 두 카테고리는
같은 보드의 앞뒤면이고 배경·조명이 같으므로, 갈리는 이유가 "배경이 달라서"가
아니라 **정상 패치 자체가 다른 것** 하나로 좁혀집니다.
`receive(duplicate_requires_same_line=True)` 의 근거가 여기 있습니다.

뒤집으면 위험 신호입니다 — `resolve_bank` 가 품목을 잘못 물면 **전 건이
불량으로 뜹니다**(과검 100%). 요란하게 틀려 알아채기는 쉽습니다.

맥(mps)에서 같은 명령을 돌려 대조했습니다. **뱅크 행수가 4,704 로 정확히
같습니다** — coreset 이 장치를 타지 않는다는 뜻이고 재현성 검사가 설 근거입니다.
점수는 부동소수점 차이로 셋째 자리가 갈리지만 판정은 안 바뀝니다.

**coreset 이 증폭하는 것은 "결함이 있는 이미지"이지 "결함 그 자체"가
아닙니다.** 합성에서 나온 "12.5% → 50~70%" 는 **VisA 실측에서 반증됐습니다.**

| | 오염 이미지 비중 | 그 출신 패치가 뱅크에서 | 결함 **위** 패치가 뱅크에서 |
|---|---|---|---|
| 합성, coreset 0.1 | 12.5% | 70.6% | (구분해 재지 않음) |
| **VisA, coreset 0.01** | 3.2% | 8.3% (2.6배) | **0.1%** (6/4,861) |

오염 이미지 출신은 늘지만 결함 위 패치는 오히려 묽어집니다. 그래서 **고립도로
오염을 못 찾고**(후보 1개 중 0개), **이미지 단위 제거는 정상 패치 98.5% 를
함께 버립니다.** 자세한 것은 `docs/실험_판별5번.md` 4·5·6장.

`coreset_ratio 0.1` 요청은 `DEFAULT_MAX_BANK_SIZE = 20,000` 상한에 걸려 실제로는
4.1% 입니다(`bank.meta["coreset_capped"]`).

**임계값 스윕은 "왜 안 되는지"를 말해주지 못합니다.** VisA 실측에서 오염된
뱅크는 "임계값 조정으로 해결 불가"로 나왔습니다(AUROC 0.883, 전건 검출에
과검률 59.5%). 여기까지는 잘 작동합니다. 문제는 **정상 분포 중첩에서도 똑같이
"해결 불가"가 나온다**는 것입니다. 두 원인은 조치가 정반대입니다 — 오염은
제거 후 재구성, 중첩은 재구성 금지. 스윕은 그 갈림을 만들지 못하고 역추적이
만듭니다. 그래서 진단이 **역추적을 임계값보다 먼저** 봅니다.

합성 데이터에서는 오염된 뱅크도 AUROC 1.000 에 "해결 가능"이 나왔습니다.
결함이 지나치게 뚜렷해 상대 순서가 유지된 탓이며 **실데이터에서는 재현되지
않습니다.** 합성 결과를 근거로 삼지 마세요.

**greedy coreset 은 O(k·N)** 이라 실데이터에서 비율을 크게 잡으면 끝나지
않습니다. `build_bank(max_bank_size=...)` 상한이 걸려 있고, 걸리면 meta 에
남습니다.

**뱅크는 `split="bank"` 전부로 세우지 않습니다 — 거기서 150장만 뽑습니다.**

이 규칙이 `app/pipeline.py` 의 `VISA_NORMAL_COUNT` 안에만 있어서 한 번 사고가
났습니다. 공장 생성기는 이미지의 70% 를 `split="bank"` 로 찍어 **라인당
3,750장**이 되는데, 그걸 그대로 분모로 잡으면 오염률이 40배 옅어 보입니다.
장영진이 시나리오에 적은 오염 2~5장이 "0.08% 라 검출 한계 아래"로 읽혔는데,
**150장 기준으로는 1.3~3.2% 라 실측(3.2%) 그대로였습니다.**

| 시나리오 | 오염 | 뱅크 150장 기준 | 후보 3,750장 기준 |
|---|---|---|---|
| SC-BC-001 | 3 | **1.96%** | 0.08% |
| SC-BC-002 | 5 | **3.23%** | 0.13% |
| SC-BC-003 | 2 | **1.32%** | 0.05% |
| SC-BC-004 | 4 | **2.60%** | 0.11% |

전부를 쓸 수 없는 이유가 둘입니다. greedy coreset 이 O(k·N) 이라 수천 장이면
끝나지 않고, **실측 AUROC 0.998 이 정상 150장에서 나온 값**이라 크기를 바꾸면
그 수치를 근거로 못 씁니다.

값은 `data/build_factory.py` 의 `BANK_BUILD_SIZE` 와 `app/pipeline.py` 의
`VISA_NORMAL_COUNT` 두 곳에 있습니다. 두 벌이라 어긋날 수 있어
`tests/test_factory_build.py` 가 같은 값인지 검사합니다. **조회 계층 실구현이
붙을 때도 같은 값을 써야 합니다.**

**`inspect` 는 파이썬 표준 라이브러리 이름**이라 패키지로 못 씁니다.
그래서 `inspection` 입니다.
