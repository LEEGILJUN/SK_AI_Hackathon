## 1. 무엇을 바꿨나

### 라인별 구성표 하나로 모았습니다

`app/pipeline.py` 의 `DEMO_LINES` 입니다. 라인마다 무엇을 심을지가 여기
한 곳에 있고, 공장·조회 계층·시험이 전부 이 표를 봅니다.

| 라인 | 품목 | 정상 장수 | 야간 로트를 뱅크에 | 혼입 | 임계값 | 나와야 하는 원인 |
|---|---|---|---|---|---|---|
| 1라인 | pcb1 | 150 | 넣음 | 2장 | 기본값 | 뱅크 오염 |
| 2라인 | pcb2 | 210 | **안 넣음** | 없음 | 2.60 | 커버리지 부족 |
| 3라인 | pcb3 | 150 | 넣음 | 없음 | 기본값 | 없음 (재구성이 답이 아닌 자리) |
| 4라인 | pcb4 | 150 | 넣음 | 없음 | 기본값 | 없음 |

### 오염이 1라인에 남은 이유 — 제안과 다릅니다

보고서는 1라인을 커버리지, 2라인을 오염으로 제안했습니다. **그대로 하면
기본 시연이 1단계에서 멈춥니다.**

`data/issue_history.jsonl` 에 `ISS-0053`(line_02 · pcb2 · scratch · 해결됨)이
있어 2라인 스크래치 이슈는 중복으로 차단됩니다. 네 라인 중 **스크래치가
해결 이력에 없는 라인은 1라인뿐**입니다(`ISS-0044` 미해결). 그 파일은
데이터 담당 소유라 여기서 고치지 않았습니다.

pcb1 을 커버리지 쪽으로 미신 근거는 정상 150→700장에서 과검이 41.3%→1.0%
로 갈린다는 것이었는데, **그 폭은 아직 안 샀습니다.** 700장 뱅크는 greedy
coreset 이 O(k·N) 이라 세우는 값이 크고, 그것을 재는 것은 그쪽 몫입니다.
올리실 때는 표의 `normal_count` 하나만 고치면 됩니다.

### 야간 로트를 만들었습니다

전에는 정상 이미지에 로트를 **번갈아** 붙였습니다. 그러면 어느 로트든
뱅크 안에 있어서 **"이 조건이 뱅크에 없다"가 성립할 수 없었습니다.** 지금은
뒤쪽 30% 를 야간 로트로 두고, 커버리지 라인만 그것을 뱅크에서 뺍니다.
접수되는 결함도 그 로트에서 나옵니다.

### 뱅크 구성 이력이 실제 구성에서 나옵니다

`lookup/mock.py` 가 상수 하나를 돌려주고 있었고, 거기 적힌 로트
(`LOT-20260602-004`)는 **가상 공장에 없는 로트**였습니다. 판별 6번의 답이
공장 구성과 무관하게 정해져 있었다는 뜻입니다. 지금은
`DemoFactory.bank_profiles()` 가 뱅크에 실제로 든 이미지에서 만듭니다.

### 판별 3번의 임계값이 조회에서 옵니다

실행 인자 하나가 모든 품목에 쓰이고 있었습니다. 보고서 3장대로
`get_threshold(라인, 품목, 뱅크)` 가 준 값을 씁니다. 못 찾으면 실행 인자를
그대로 씁니다.

### 저장소가 옛 구성의 뱅크를 돌려주지 않습니다

저장소는 특징 설정만 대조합니다. **구성을 바꿔도 어제 세운 뱅크가 그대로
실립니다.** 그러면 시연은 새 구성이라 말하고 뱅크는 옛 구성인 상태가 되고,
그것이 화면에서는 안 보입니다. v1 판은 구성이 다르면 다시 세웁니다
(운영본 v2 이상은 그대로 둡니다 — 사람이 승인해 넘긴 판이라서).

**그래서 그쪽 `banks/` 의 v1 판들은 이번에 한 번 다시 섭니다.** 얼마나
걸리는지가 아래 확인 항목의 첫 번째입니다.

### 합성 무늬에 pcb2·pcb3·pcb4 를 넣었습니다 (맥 전용 경로)

`tests/synthetic.py` 의 무늬표에 pcb1 밖에 없어서 **2·3·4라인이 전부 캡슐
무늬로 서 있었습니다.** 생김새가 같은 것으로 끝나지 않았습니다 — 캡슐
무늬(110/165)에 결함 얼룩(25)이 찍히면 대비·선명도가 z=5·z=10 으로 튀어
**판별 2번이 화질 이탈로 읽고 진단이 언제나 설비·광학으로 나왔습니다.**
라인마다 다른 원인을 심어도 그 앞에서 전부 가려집니다. VisA 로 서면 이
경로는 안 밟습니다.

## 2. 4090 에서 확인해 주실 것

맥에서는 합성으로만 확인했습니다. **아래는 전부 실데이터라야 답이 나옵니다.**

```
git fetch origin && git rev-parse origin/main    # 해시를 눈으로 대조
python -m pytest tests/ -q

python scripts/run_demo.py                                    # 1라인 · 뱅크 오염
python scripts/run_demo.py --item line_02/pcb2                # 2라인 · 커버리지 부족
python scripts/run_demo.py --item line_03/pcb3                # 3라인 · 멈춰야 함
```

**`--item` 이 이제 접수 제품까지 그 라인 것으로 바꿉니다.** 전에는 제품명이
기본 라인 것으로 남아 MES 가 엉뚱한 것을 찾았습니다. `--threshold` 기본값도
비웠습니다 — 값을 적으면 그것이 이기고, 안 적으면 품목별 값을 씁니다.
**전에는 2.20 이 박혀 있어 품목별 임계값이 영영 안 쓰였습니다.**

판별 5번을 모델에 물으면 2라인은 "진짜 정상품"이 나와야 커버리지 부족으로
갑니다. 안 나오면 `--patch-override genuine_normal` 로 한 번 더 봐 주세요.
**판별 1번에서 멈추는 것은 따로 남은 문제입니다**(`docs/이어서작업.md` 3장 1번).

### ① 뱅크가 다시 서는 데 얼마나 걸리나

구성이 바뀌었으므로 v1 판 넷이 다시 섭니다. 전에는 셋에 108초였습니다.
**시연 첫 기동이 몇 초인지**를 적어 주세요. 너무 길면 `normal_count` 를
낮추는 것으로 되돌릴 수 있습니다.

### ② 2라인이 실제로 미검을 내나 — 이번 변경의 급소입니다

커버리지 부족 라인은 **뱅크가 야간 조건을 몰라 정상품 점수가 높게 나오고,
현장은 과검을 못 견뎌 임계값을 올려 둔** 상태를 흉내냅니다. 그 상태에서
결함이 임계값 아래로 묻히는 것이 이 라인의 미검입니다.

**임계값 2.60 은 합성에서 미검이 생기는 자리이고 VisA 값이 아닙니다.**
그쪽 `docs/data_품목별임계값.json` 에 따르면 깨끗한 700장 뱅크의 pcb2
과검 1% 지점이 2.153 인데, 우리 뱅크는 117장에 야간 조건이 빠져 있어
그 값이 그대로 맞을 이유가 없습니다.

    2라인으로 이슈를 넣었을 때 재검사가 미검을 몇 장 내는가
    0장이면 진단까지 못 갑니다 — 그때는 임계값을 얼마로 해야 미검이 생기는가

`DEMO_LINES` 의 `threshold=2.60` 한 자리입니다.

### ③ 보충이 몇 장이고 재구성이 시연 안에서 끝나나

2라인 야간 로트는 63장이고 그중 4장은 홀드아웃이라 **보충 후보가 59장**
입니다. 그 59장을 임베딩하고 176장으로 coreset 을 다시 도는 시간이
시연 중에 흐릅니다. 길면 `night_lot_share` 를 낮춥니다.

### ④ 보충 뒤에 성능이 실제로 좋아지나

합성에서는 게이트 통과 · 신구 비교 6장 새로 검출이 나왔습니다. **합성
결과를 근거로 쓰지 마세요.** VisA 에서 다음을 봐 주세요.

    게이트 통과 여부와 그때의 후보 임계값
    신구 비교에서 갈린 장수 (새로 검출 / 새로 놓침)
    과검이 줄었는가

### ⑤ 1라인 오염 시연이 그대로인가

**예선 영상의 경로입니다.** 여기가 흔들리면 되돌려야 합니다.
홀드아웃 정상 4장이 전과 다른 이미지로 바뀌었으므로(주간 로트에서 뗍니다)
게이트·신구 비교 숫자는 조금 움직일 수 있습니다. 원인이 뱅크 오염으로
나오고 열 단계를 완주하는지만 봐 주세요.

### ⑥ 3·4라인이 멈추나

재구성까지 가지 않고 "재구성이 답이 아니다"로 끝나야 합니다. 합성에서는
임계값 문제로 나왔습니다.
