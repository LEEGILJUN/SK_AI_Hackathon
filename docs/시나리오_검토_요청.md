# 시나리오 검토 요청 — 진단 규칙 측정 결과

작성 2026-08-13 · 이길준 → 장영진
대상 `data/scenarios.yaml` (실제 시나리오 24건 + 예시 템플릿 1건)

시나리오를 받아 진단 규칙에 걸어 봤습니다. **결과 자체는 나쁘지 않은데, 정하고
가야 할 것이 네 가지 나왔습니다.** 그중 셋은 정답 파일 쪽이라 임의로 고치지
않고 남겨 두었습니다.

---

## 1. 무엇을 쟀는가

각 시나리오의 `ground_truth.evidence` 7항목을 **그대로** `decide()` 에 넣고,
나온 원인을 `ground_truth.cause` 와 대조했습니다.

이미지·메모리 뱅크·조회 계층·시각 언어 모델은 **하나도 쓰지 않았습니다.**
그래서 이 수치는 **진단 규칙만의 정확도**입니다. 증거를 얼마나 잘 모으는가와는
별개이며, 규칙이 틀리면 이미지 성능을 아무리 올려도 결과는 틀립니다.

임계값 스윕은 넣지 않았습니다. 시나리오에 스윕 결과가 없기 때문이며,
이것이 아래 (4)번입니다.

재현은 이 한 줄입니다.

```bash
python scripts/measure_rules.py
```

## 2. 결과

```
원인 일치        19/24
재구성 여부 일치 22/24
금지 행위 위반   0건
```

| 원인 | 정확도 |
|---|---|
| 뱅크 오염 | 4/4 |
| 커버리지 부족 | 4/4 |
| 설비·광학 | 4/4 |
| 기준 문제 | 4/4 |
| 임계값 문제 | 2/4 |
| **정상 분포 중첩** | **1/4** |

**금지 행위 위반 0건이 가장 중요한 숫자입니다.** 재구성하면 안 되는 케이스에서
`rebuild_bank` 를 한 번도 부르지 않았습니다. "하지 말아야 할 때 멈추는가"는
지켜지고 있습니다.

**틀린 5건이 전부 임계값 ↔ 정상 분포 중첩 갈림 하나에 몰려 있습니다.**
뱅크 오염이 4/4인데 그 짝인 정상 분포 중첩이 1/4입니다.
원인은 아래 (1)과 (4) 두 가지이며, **둘 다 정답 파일 쪽에서 정해 주셔야
풀립니다.**

```
SC-TH-001  threshold → normal_overlap   (score_ratio=0.89)
SC-TH-003  threshold → normal_overlap   (score_ratio=0.91)
SC-NO-002  normal_overlap → 보류         (score_ratio=0.95)
SC-NO-003  normal_overlap → 보류         (score_ratio=0.96)
SC-NO-004  normal_overlap → threshold    (score_ratio=0.98)
```

## 3. 정해 주셔야 할 것 네 가지

### (1) 정상 분포 중첩에서 결함이 눈에 보이는가

`SC-NO-002`, `SC-NO-003` 에 `defect_visible: false` 가 들어 있습니다.
지금 진단 코드는 이 값을 보면 판정을 멈춥니다.

> "이미지에서 결함이 확인되지 않았다. 미검출이 아니라 접수 오류이거나
> 다른 이미지가 첨부됐을 수 있다."

두 관점이 다 말이 됩니다.

- **시나리오 관점** — 정상 분포 중첩은 형상이 정상품과 유사해서 못 잡는
  원인이니, 사람 눈에도 안 보일 수 있다
- **코드 관점** — 사람이 불량이라고 접수했는데 이미지에서 결함이 안 보이면
  접수 자체를 먼저 확인해야 한다

어느 쪽이 맞는지는 **원인 분류 체계의 문제**라 장영진 님 판단입니다.
정해 주시면 그쪽으로 맞추겠습니다. 채점을 맞추려고 저희가 임의로 진단 코드를
고치지는 않겠습니다.

### (2) `score_vs_threshold` 와 `score_ratio` 가 서로 어긋납니다

두 필드가 한 값으로 갈리지 않습니다.

| 시나리오 | score_ratio | 라벨 |
|---|---|---|
| SC-EQ-003 | 0.95 | near |
| SC-NO-002 | 0.95 | **below** |
| SC-TH-003 | 0.91 | below |
| SC-TH-002 | 0.94 | near |

**같은 0.95가 near 이기도 below 이기도 합니다.** 어떤 경계값을 잡아도 라벨을
전부 재현할 수 없고, 24건 중 7건이 어긋납니다.

코드는 `score_ratio` 가 0.9 이상이면 `near` 로 계산합니다
(`inspection/types.py` 의 `score_position`, `near_ratio=0.9`).
라벨을 보면 장영진 님은 0.94~0.98 사이를 경계로 보고 계신 듯합니다.

**제안** — `score_ratio` 를 정답으로 두고 `score_vs_threshold` 는 빼거나
파생값으로 표시합니다. 실제 운영에서도 사람이 라벨을 붙이는 것이 아니라
`score_position()` 이 비율에서 계산하므로, 그러면 **경계값 하나만 합의하면
됩니다.** 지금 0.9가 맞는지, 더 좁혀야 하는지 의견 주십시오.

확인은 이 명령으로 할 수 있습니다.

```bash
python scripts/measure_rules.py --computed
```

### (3) `SC-BC-001` 이 두 번 있습니다

파일 끝에 골격 시절 예시 시나리오가 그대로 남아 있고, ID 가 앞의 실제
시나리오와 같습니다.

```yaml
  # 예시 1건 — 뱅크 오염 (MVP 필수 시나리오)
  # 아래 형식을 그대로 복제해 나머지를 채웁니다.
  - id: SC-BC-001        ← 앞의 실제 시나리오와 같은 ID
```

**채점 스크립트가 ID 를 키로 모으는 순간 하나가 조용히 덮입니다.**
`check_scenarios.py` 에 ID 중복 검사를 넣어 다음부터는 잡히게 했습니다.

같이 손보면 좋을 것 두 곳입니다.

- 파일 머리 — `현재 상태: 필드 정의와 예시 1건만 담긴 골격입니다`
- 파일 끝 — `# TODO(장영진): 나머지 19건 이상`

둘 다 24건이 채워지기 전의 표기입니다.

### (4) 임계값 ↔ 정상 분포 중첩은 `score_ratio` 로 못 가릅니다 — 스윕 결과가 필요합니다

(2)번을 파고들다 더 근본적인 것이 나왔습니다. 두 원인의 `score_ratio` 분포가
이렇습니다.

```
threshold        [0.89, 0.91, 0.94, 0.97]
normal_overlap   [0.93, 0.95, 0.96, 0.98]
```

**정상 분포 중첩이 오히려 임계값에 더 가깝고, 두 분포가 0.93~0.97 에서
겹칩니다.** 지금 진단 코드는 반대로 봅니다 — 임계값에 가까우면(near) 조금만
내리면 잡히니 임계값 문제, 크게 못 미치면(below) 정상 분포 중첩.

두 해석이 다 말이 됩니다.

- **코드 쪽** — "임계값 문제 = 이상 점수는 높으나 임계값 아래". 0.98 이면
  조금만 내려도 잡힌다
- **장영진 님 쪽** — 임계값이 과보수로 설정됐으면 멀쩡한 결함도 0.89 까지
  밀려난다. 반대로 정상 분포 중첩은 결함이 정상 분포 가장자리에 붙어 0.98 이 된다

`SC-TH-001` 을 "threshold 과보수 설정"으로 쓰신 걸 보면 후자가 의도인 듯합니다.

**어느 쪽이든 `score_ratio` 하나로는 원리적으로 못 가릅니다.** 두 분포가
겹치기 때문입니다. 그래서 저희가 규칙을 라벨에 맞추는 것은 하지 않았습니다 —
그러면 정답 파일에 진단 로직을 맞추는 것이 되고, 19/24 라는 숫자가 의미를
잃습니다.

**가르는 방법은 임계값 스윕입니다.** "임계값을 내려 목표 검출률에 닿는가,
그때 과검률이 감당 가능한가". 이게 두 원인의 정의 그대로이고
`assess_threshold_feasibility()` 가 이미 하는 일입니다.

다만 **시나리오에 스윕 결과가 없습니다.** 그래서 지금은 진단 경로에 스윕을
물려도 24건 측정에서는 아무것도 바뀌지 않습니다. 아래 두 필드를 넣어 주시면
`SC-TH-001`·`SC-TH-003`·`SC-NO-004` 세 건이 원리대로 갈립니다.

```yaml
      evidence:
        ...
        threshold_sweep:
          achievable: false      # 임계값 조정으로 목표 검출률에 닿는가
          resulting_fpr: 0.71    # 그때 과검률
```

`threshold` 케이스는 `achievable: true` 에 낮은 과검률,
`normal_overlap` 케이스는 `achievable: false` 에 높은 과검률이 될 것입니다.
값은 실제 데이터로 재는 것이 가장 좋지만, 아직 가상 공장이 없으므로
도메인 판단으로 넣으셔도 됩니다.

## 4. 저희 쪽에서 할 것

- **임계값 스윕을 진단 경로에 물립니다.** 코드에 이미 갈림길이 있는데 입력이
  안 들어가고 있습니다. 다만 (4)번대로 **시나리오에 스윕 결과가 들어와야
  측정에 반영됩니다.** 물리는 것만으로는 24건 점수가 바뀌지 않습니다.
- **웹 데모를 도구 호출 경로로 바꿉니다.** 지금은 함수를 순서대로 부르는
  파이프라인이라 "에이전트가 판단한다"가 성립하지 않습니다.
- `check_scenarios.py` 에 **ID 중복 검사**를 넣었습니다. 이번에 한 번 통과시킨
  검사는 다음에도 통과시킵니다.

## 5. 손대지 않은 것

`data/scenarios.yaml` 은 채점 기준 파일이라 **한 글자도 고치지 않았습니다.**
위 (1)(2)(3)(4) 모두 확인 후 진행 부탁드립니다.

논리 검사라, 그 조합이 현장에서 실제로 발생하는지와는 무관하기 때문입니다.
