# 거버넌스 기록 — 무엇을 왜 바꿨는가가 남는가 (작업 22)

검사 모델을 바꿨는데 **왜 바꿨는지가 안 남으면**, 반년 뒤에 그 판단을 되짚을
수 없습니다. 되짚을 수 없으면 잘못된 변경을 찾아낼 수도, 옳았던 변경을 근거로
쓸 수도 없습니다.

이 문서는 **지금 실제로 남는 것**을 적고, **안 남는 것**을 함께 적습니다.
설계안이 아니라 현황이며, 구멍은 구멍이라고 씁니다.

---

## 1. 한 번의 변경에서 남는 것

이슈 하나가 접수되어 뱅크가 바뀌기까지 열 단계가 돌고, 각 단계가 기록을
남깁니다. 전부 `agents/release.py` 의 배포 패키지 한 폴더에 모입니다.

| 파일 | 무엇이 남는가 | 만드는 곳 |
|---|---|---|
| `diagnosis.json` | 원인 6종 중 무엇인가 · 판별 7항목의 값과 출처 · 확신도 · 보류 사유 | `agents/diagnose.py` |
| `curation_plan.json` | 뱅크에서 무엇을 빼고 무엇을 넣기로 했는가 · 각각의 근거 | `agents/curate.py` |
| `rebuild_record.json` | 어느 판에서 어느 판으로 · 실제로 제거·추가된 이미지 목록 · 유지 장수 | `agents/rebuild.py` |
| `gate.json` | 통과 기준 각 항목의 값과 판정 | `agents/gate.py` |
| `shadow.json` | 신·구 뱅크가 갈린 건 목록 | `inspection/shadow.py` |
| `reproducibility.json` | 같은 근거로 10회 반복했을 때 판정이 같았는가 | `agents/gate.py` |
| `defect_distribution.json` | 결함이 특정 로트·설비에 몰려 있는가 | 조회 계층 |
| `승인요청.md` | 사람이 읽는 요약과 승인 후 실행할 명령 | `agents/release.py` |
| `bank.npz` · `bank_meta.json` | 새 뱅크 자체와 그 구성 이력 | `inspection/bank.py` |

### 재학습 의도가 어디에 남는가

작업 정의의 "재학습 의도 기록 구조"가 이 셋입니다.

```
왜 바꿨나    diagnosis.json    원인과 판별 7항목의 값
무엇을 바꿨나 rebuild_record.json  제거·추가된 이미지 목록
누가 시켰나   rebuild_record.json  triggered_by (이슈 원문 그대로)
```

`triggered_by` 에 **이슈 원문이 통째로** 들어갑니다. 요약이 아니라 원문인
이유는, 요약하는 순간 무엇을 근거로 판단했는지가 사람 손을 한 번 거치기
때문입니다.

### 뱅크 자체에도 계보가 남습니다

`bank_meta.json` 이 벡터와 같은 폴더에 있습니다. 배포 패키지를 잃어도 뱅크만
있으면 되짚을 수 있습니다.

```json
{
  "bank_version": "pcb1-01-v2",
  "rebuilt_from": "pcb1-01-v1",
  "cause": "bank_contamination",
  "removed_images": ["...", "..."],
  "added_images": [],
  "triggered_by": "line_01 에서 ...",
  "approved_for_deploy": false,
  "feature_config": { "backbone": "...", "crop": 512, ... },
  "baseline": { "median": [...], "mad": [...] }
}
```

`feature_config` 가 함께 있어서 **다른 설정으로 만든 뱅크를 잘못 쓰는 것을
막습니다.** 실제로 입력 크기를 448 에서 512 로 바꿨을 때 옛 뱅크가 검사를
통과해 다른 척도로 점수를 내던 일이 있었고, 그 뒤로 양쪽 키를 다 대조하게
고쳤습니다.

## 2. 시간을 따라가는 기록

한 번의 변경이 아니라 **여러 번의 변경이 쌓인 것**을 보는 자리가 둘입니다.

### 뱅크 저장소 — 어느 판이 언제 운영에 쓰였나

```
banks/pcb1-01/
  pcb1-01-v1_20260815-2004_cad872/
  pcb1-01-v2_20260816-0910_cad872/
  CURRENT → pcb1-01-v1_20260815-2004_cad872
```

폴더 이름에 **판 번호 · 만든 시각 · 설정 지문**이 들어갑니다. 판을 지우지
않으므로 계보가 그대로 쌓이고, 되돌리기가 파일 이동이 아니라 `CURRENT` 한
줄 되돌리기입니다.

`scripts/scan_bank_history.py` 가 폴더만 보고 이력을 복원합니다. 이력 파일이
있으면 확정, 벡터만 있으면 **추정으로 표시**합니다 — 역추정한 것을 확정처럼
쓰면 그 위에서 내린 판단이 전부 흔들립니다.

### 이슈 이력 그래프 — 같은 문제가 또 왔는가

`data/issue_history.jsonl` 한 줄이 한 건입니다.

```json
{
  "issue_id": "ISS-0042",
  "line": "line_02", "object_name": "pcb1", "defect_type": "scratch",
  "cause": "bank_contamination",
  "action": "혼입 이미지 2장 제거 후 뱅크 재구성",
  "resolved": true,
  "occurred_at": "2026-04-08",
  "summary": "..."
}
```

**역할은 중복 차단 하나입니다.** 과거가 비슷하다고 이번 원인을 그것으로
정하면 진단이 유사도 맞히기가 됩니다 — 원인은 판별 7항목이 냅니다.

끊는 조건이 넷이고 **넷이 다 맞아야** 합니다. 같은 라인 · 같은 품목 · 같은
결함유형 · 해결됨. **다른 라인의 같은 증상은 중복이 아닙니다** — 라인마다
뱅크가 따로이므로 1라인이 오염됐다고 2라인도 그렇다는 뜻이 아닙니다.

## 3. 안 남는 것 — 지금의 구멍

**여기가 이 문서에서 제일 중요한 절입니다.** 있는 것만 적으면 없는 것이
안 보입니다.

### ~~(1) 승인 기록이 없습니다~~ → 만들었습니다

`banks/<품목>/DECISIONS.jsonl` 에 한 줄씩 덧붙습니다.

```json
{"at": "2026-08-16T15:00:00", "by": "이길준",
 "previous": "pcb1-01-v2_20260816-1000_cad872",
 "to": "pcb1-01-v1_20260815-2004_cad872",
 "reason": "과검 증가로 되돌림", "rollback": true}
```

**누가와 왜가 없으면 전환이 거부됩니다.** `--by` 와 `--reason` 이 필수이고,
없으면 스크립트가 이유를 적어 주고 멈춥니다 — 누가 무엇을 근거로 승인했는지가
안 남으면 "배포는 사람이 승인한다"는 경계가 말뿐이 됩니다.

**되돌리기는 판 번호로 알아서 표시됩니다.** 낮은 번호로 가면 `rollback: true`
입니다. 되돌린 횟수가 세어지므로 **자주 되돌린 품목은 게이트 기준이 느슨하다는
신호**로 읽을 수 있고, 목록 화면이 두 번 이상이면 그렇게 적습니다.

덧붙이기만 하고 고치지 않습니다. 한 줄이 망가져도 나머지는 읽습니다.

```
python scripts/switch_bank.py --item pcb1-01 --history
```

**에이전트와 스케줄러는 이 기록도 못 남깁니다.** 남길 수 있으면 "사람이
승인했다"는 기록이 자동으로 생깁니다. 전환을 막아 둔 것과 같은 이유로
시험이 검사합니다.

### (2) 자동 실행이 남긴 것과 사람이 시작한 것이 구분되지 않습니다

스케줄러가 만든 이슈도 사람이 접수한 것과 같은 경로로 갑니다. 전용 경로를
만들지 않은 것은 의도한 설계입니다 — 두 벌이 되면 한쪽만 고쳐집니다.

다만 기록에서도 구분이 안 됩니다. `triggered_by` 에 이슈 원문이 들어가는데,
스케줄러가 만든 문장인지 사람이 쓴 것인지 **문장을 읽어야 압니다.**

플래그 하나면 됩니다. `"origin": "scheduler" | "human"`.

### (3) 진단이 보류된 건이 안 쌓입니다

판별 항목이 모자라 보류된 건은 배포 패키지가 안 만들어지므로 **아무 기록도
안 남습니다.** 그런데 보류야말로 쌓아서 봐야 하는 것입니다 — 같은 이유로
계속 보류된다면 그 판별 항목에 구멍이 있다는 뜻입니다.

실제로 지금 그런 상태가 있습니다. 판별 1번이 `not_visible` 이면 진단이
멈추는데, 기판에서 위치 추정이 상위 1자리 3/10 이라 **자주 걸릴 자리**입니다.
몇 번 걸렸는지가 안 쌓이면 그것을 고칠 근거가 안 모입니다.

### (4) 기준이 바뀐 이력이 파일에만 있습니다

`data/criteria.yaml` 은 `effective_from`/`effective_to` 로 버전을 쌓게 설계돼
있고, 진단이 **그 시점에 유효했던 기준으로** 판정합니다. 지금 기준으로 과거를
보면 "기준 문제" 원인을 영영 못 찾기 때문입니다.

`data/gate.yaml` 에는 그 구조가 없습니다. 게이트 기준을 언제 왜 바꿨는지는
git 이력에만 있고, 그건 운영자가 볼 자리가 아닙니다.

## 5. 남기지 않는 것

기록을 늘리는 것이 언제나 옳지는 않습니다. 아래는 **일부러 안 남깁니다.**

- **사내 공정 조건 · 장비 공급사 · 생산 거점 · 사내 결함 정의 체계** —
  이 저장소의 어떤 기록에도 넣지 않습니다
- **원본 이미지 사본** — 기록에는 경로만 남깁니다. 이미지를 복사해 쌓으면
  용량이 감당이 안 되고, 원본이 바뀌었을 때 어느 것이 진짜인지 갈립니다
- **언어 모델이 쓴 서술** — 판정에 영향을 주지 않는 문장이라 기록의 근거로
  쓰지 않습니다. `narrative` 필드에 따로 두고 판정과 섞지 않습니다
