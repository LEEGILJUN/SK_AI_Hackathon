# 운영 임팩트를 어떻게 셈했는가

**본선 배점의 SUPEX 추구 30점 중 "달성하고자 하는 목표의 수준"과 "문제
해결에 따른 임팩트의 범위"에 쓰는 근거입니다.**

기대 효과를 수치로 적으라는 요구는 흔하고, 그때 나오는 숫자가 대개 어디서
왔는지 알 수 없습니다. **몇 % 절감이라고 적혀 있는데 무엇을 재서 나온
것인지 되짚을 수 없으면 그 숫자는 근거가 아닙니다.**

그래서 둘을 갈라 놓았습니다.

```bash
python scripts/estimate_impact.py
```

## 1. 측정에서 온 것

저장소에서 계산합니다. 사람이 넣지 않습니다.

| 항목 | 값 | 어디서 |
|---|---|---|
| 재구성이 답인 경우 | **8/24 (33.3%)** | `data/scenarios.yaml` 의 정답 라벨 |
| 재구성이 답이 아닌 경우 | **16/24 (66.7%)** | 같은 파일 |
| 그 16건에서 뱅크를 건드린 횟수 | **0건** | `scripts/measure_rules.py` |
| 진단 원인 일치 | **22/24** | 같은 스크립트 |
| 신구 비교 확인 대상 | **14장 중 1장 (92.9% 감소)** | 실모델 완주 기록 |
| 전 구간 자동 실행 | **151초** | 4090 실측, 도구 10개 완주 |

**재구성이 답인 비율은 우리 판정이 아닙니다.** 도메인 담당이 시나리오에
걸어 둔 정답 라벨에서 셉니다. 그래서 "재구성이 답인 경우가 얼마나 되는가"의
근거로 쓸 수 있습니다.

## 2. 가정에서 온 것

현장 값이라 우리가 모릅니다. **도메인 담당이 확정하면 그때 명령의 인자만
바꿉니다.**

| 가정 | 기본값 | 왜 이 값인가 |
|---|---|---|
| 연간 이슈 | 100건 | 라인 하나 기준. 확인 필요 |
| 원인 파악 | 4시간 | 이미지를 열어 보고 짐작하기까지 |
| 재구성 | 6시간 | 데이터 선별부터 배포 후보까지 |
| 성능 확인 | 8시간 | 좋아졌는지 사람이 보는 시간 |
| 승인 검토 | 1시간 | 승인 문서를 읽고 판단 |
| 지금의 재구성 비율 | 100% | 미검출이 오면 재학습을 건다는 전제 |

## 3. 계산

```
지금    원인 파악 + (재구성 비율 × (재구성 + 성능 확인))
우리    자동 진단 + (33.3% × (재구성 + 성능 확인 축소분)) + 승인 검토
```

**우리 쪽에도 사람 시간이 남습니다.** 승인은 사람이 하고, 신구 비교에서
갈린 건도 사람이 봅니다. 그 둘을 빼지 않았습니다. 무인 운영을 만들지 않는
것이 이 과제의 설계이므로 계산에서도 빼면 안 됩니다.

### 기본 가정에서

| 항목 | 지금 | 우리 방식 |
|---|---|---|
| 한 건에 드는 사람 시간 | 18.0시간 | **3.2시간** |
| 연간 100건 | 1,800시간 | **323시간** |

건당 14.8시간, 연간 1,477시간이 줄어듭니다.

## 4. 가정이 틀리면 얼마나 달라지는가

**가장 크게 흔들리는 가정은 "지금은 미검출이 오면 재학습을 건다"입니다.**
현장이 이미 선별적으로 재학습한다면 절감 폭이 줄어듭니다.

| 지금의 재구성 비율 | 지금 | 우리 방식 | 절감 |
|---|---|---|---|
| 30% | 8.2시간 | 3.2시간 | 5.0시간 (61%) |
| 50% | 11.0시간 | 3.2시간 | 7.8시간 (71%) |
| 100% | 18.0시간 | 3.2시간 | 14.8시간 (82%) |

**어느 가정에서도 방향은 같습니다.** 그리고 1장의 두 줄은 가정과 무관하게
그대로입니다.

## 5. 시간으로 환산되지 않는 것

**이쪽이 더 중요할 수 있습니다.** 시간은 가정 위에 있지만 아래는 측정에서
바로 나옵니다.

### 잘못된 재구성을 막습니다

재구성이 답이 아닌 16건에서 뱅크를 건드린 횟수가 0입니다. 이것이 막는 것은
시간만이 아닙니다. **설비·광학 문제인데 뱅크를 다시 만들면 원인은 그대로
있고 뱅크만 흔들립니다.** 정상 분포 중첩에서 정상 패치를 잘못 제거하면
과검이 늘어납니다.

### 확인해야 할 것을 줄입니다

양산 데이터에는 정답 라벨이 없습니다. 새 뱅크가 좋아졌는지 확인하려면
사람이 봐야 하는데, 신구 비교가 **판정이 갈린 건만** 뽑아 줍니다. 실측에서
14장 중 1장이었습니다.

### 잘못 잡던 것이 얼마나 줄어드는가

도입 초기 뱅크(정상 150장)와 데이터가 쌓인 뱅크(정상 700장)의 차이입니다.
4090 실측입니다.

| pcb1 | 정상 150장 | 정상 700장 |
|---|---|---|
| 과검 | **41.3%** | **1.0%** |
| AUROC | 0.839 | 0.991 |

**양품 세 장 중 한 장을 불량이라 하던 것이 백 장 중 한 장으로 갑니다.**
이 폭을 만드는 것이 커버리지 부족 진단과 조건별 보충입니다.

## 6. 확장의 범위

한 라인, 한 품목에 묶이지 않는 근거입니다.

- **품목마다 뱅크가 따로**입니다. 라인·품목을 키로 찾고 없으면 멈춥니다.
  품목이 늘어도 코드가 안 바뀝니다.
- **조회 계층이 인터페이스로 분리**돼 있습니다. 함수 8개를 구현하면 사내
  MES·이미지 저장소에 붙습니다. 끼우는 자리가 한 곳입니다.
- **모델을 설정으로 바꿉니다.** 로컬 모델과 외부 API가 같은 어댑터
  인터페이스를 씁니다. 폐쇄망이면 로컬로, 아니면 API로 갑니다.
- **예약 실행이 있습니다.** 사람이 보고하지 않아도 야간 누적분에서
  미검출을 찾아 진단까지 돌립니다.

## 7. 이 문서를 다시 만들려면

```bash
python scripts/estimate_impact.py                       # 기본 가정
python scripts/estimate_impact.py --issues-per-year 200 --diag-hours 6
python scripts/estimate_impact.py --markdown            # 표만
```

측정 값은 저장소에서 다시 계산되므로 시나리오나 실측이 바뀌면 함께
움직입니다. **가정을 바꿔도 측정 값은 안 변합니다.**
