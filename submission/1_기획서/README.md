# 1_기획서

**심사가 묻는 것: 어떤 문제를 풀려고 했나.**

## 1. 무엇을 만드는가

**검사 AI 자율 운영 에이전트.**

제조 현장에 배포된 AI 외관검사 모델이 못 잡는 불량을 만났을 때, 원인 진단
부터 데이터 선별, 메모리 뱅크 재구성, 성능 검증, 배포 패키지 생성까지를
에이전트가 스스로 수행합니다.

**검사 모델을 만드는 과제가 아닙니다.** 이미 배포된 모델을 계속 살아 있게
유지하는 운영의 문제를 다룹니다.

## 2. 문제

AI 외관검사는 배포한 날이 가장 정확합니다. 자재가 바뀌고 조명이 바뀌고
공정 조건이 흔들리면 성능이 내려갑니다. 현장에서 미검출이 보고되면 지금은
이렇게 돕니다.

1. 담당자가 이미지를 열어 본다
2. 원인을 짐작한다
3. 대개 재학습을 건다
4. 좋아졌는지 확인할 방법이 마땅치 않다

**여기서 두 가지가 낭비됩니다.** 원인을 짐작으로 정하는 것과, 재학습이
답이 아닌 경우에도 재학습을 거는 것입니다.

## 3. 근거: 재학습이 답인 경우는 여섯 중 둘뿐입니다

미검출의 원인을 여섯으로 나눴고, 그중 넷은 뱅크를 다시 만드는 것이 답이
아닙니다.

| 원인 | 조치 | 뱅크 재구성 |
|---|---|---|
| 임계값 문제 | 임계값 재조정 | 불필요 |
| 뱅크 오염 | 혼입 이미지 제거 후 재구성 | **필요** |
| 커버리지 부족 | 해당 조건 정상 이미지 추가 | **필요** |
| 정상 분포 중첩 | 기준 재정의, 전용 판별 로직, 촬영 개선 | 효과 없음 |
| 설비·광학 | 설비 점검 요청 | 차단 |
| 기준 문제 | 판정 기준 재정의 요청 | 차단 |

**진단 성능의 시험대는 재학습을 해야 할 때 하는가가 아니라, 하지 말아야
할 때 멈추는가에 있습니다.**

## 4. 왜 진단이 가능한가

PatchCore 는 정상 패치를 메모리 뱅크에 담아두고 최근접 거리로 판정합니다.
그래서 미검출이 발생하면 **그 이미지가 뱅크의 어떤 정상 패치와 가까웠는지
되짚을 수 있습니다.** 판단 근거가 모델 안에 이미 있고, 진단 에이전트는
추측이 아니라 추적으로 원인을 규명합니다.

판별 항목 7가지 중 시각 언어 모델을 쓰는 것은 2개뿐이고 나머지 5개는
조회와 계산으로 정확한 값을 얻습니다. **진단의 신뢰도는 벡터 검색이 아니라
결정론적 조회에서 나옵니다.**

## 5. 목표와 달성 수준

측정한 값입니다. 측정 조건은 [`3_검증결과`](../3_검증결과/README.md) 에
있습니다.

| 목표 | 값 | 조건 |
|---|---|---|
| 원인 진단 정확도 | **22/24** | 시나리오 24건, 정답 라벨 대조 |
| 재구성 필요 여부 판정 | **22/24** | 같은 시나리오 |
| 금지 행위 위반 | **0건** | 재구성이 답이 아닌 원인에서 뱅크를 건드린 횟수 |
| 사람이 확인할 이미지 | **14장 중 1장** | 신구 비교로 판정이 갈린 건만 추출 |
| 전 구간 자동 완주 | **10단계 / 151초** | 실모델, 도구 순서를 모델이 결정 |

## 6. 운영에서 무엇이 줄어드는가

**측정에서 온 값과 가정에서 온 값을 갈라 적습니다.** 기대 효과를 수치로
적으라는 요구에 흔히 나오는 숫자가 어디서 왔는지 되짚을 수 없는데, 그러면
그 숫자는 근거가 아닙니다. 산정 과정은 `python scripts/estimate_impact.py`
로 다시 만들 수 있습니다.

### 측정에서 온 것

| 항목 | 값 | 어디서 |
|---|---|---|
| 재구성이 답인 경우 | **8/24 (33.3%)** | 시나리오 정답 라벨 |
| 재구성이 답이 아닌 경우 | **16/24 (66.7%)** | 같은 파일 |
| 그 16건에서 뱅크를 건드린 횟수 | **0건** | 진단 규칙 채점 |
| 신구 비교 확인 대상 | **14장 중 1장 (92.9% 감소)** | 실모델 완주 |
| 잘못 잡던 것 (도입 초기 → 데이터 축적) | **과검 41.3% → 1.0%** | pcb1, 정상 150장 → 700장 |

**재구성이 답인 비율은 우리 판정이 아닙니다.** 도메인 담당이 시나리오에
걸어 둔 정답 라벨에서 셉니다.

### 가정을 얹으면

현장 시간 값은 우리가 모릅니다. 아래는 가정이며, 도메인 담당이 확정하면
같은 스크립트의 인자만 바꿉니다.

```
가정   연간 이슈 100건 · 원인 파악 4시간 · 재구성 6시간
       성능 확인 8시간 · 승인 검토 1시간
```

| 항목 | 지금 | 우리 방식 |
|---|---|---|
| 한 건에 드는 사람 시간 | 18.0시간 | **3.2시간** |
| 연간 100건 | 1,800시간 | **323시간** |

**우리 쪽에도 사람 시간이 남습니다.** 승인은 사람이 하고 신구 비교에서
갈린 건도 사람이 봅니다. 그 둘을 빼지 않았습니다.

가장 크게 흔들리는 가정은 "지금은 미검출이 오면 재학습을 건다"입니다.
현장이 이미 선별적으로 재학습한다면 절감 폭이 줄어듭니다.

| 지금의 재구성 비율 | 건당 절감 |
|---|---|
| 30% | 5.0시간 (61%) |
| 50% | 7.8시간 (71%) |
| 100% | 14.8시간 (82%) |

**어느 가정에서도 방향은 같고, 측정에서 온 값은 가정과 무관하게 그대로
입니다.**

### 시간으로 환산되지 않는 것

재구성이 답이 아닌 16건에서 뱅크를 건드리지 않는 것이 막는 것은 시간만이
아닙니다. **설비·광학 문제인데 뱅크를 다시 만들면 원인은 그대로 있고
뱅크만 흔들립니다.** 정상 분포 중첩에서 정상 패치를 잘못 제거하면 과검이
늘어납니다.

## 7. 임팩트의 범위

**한 라인, 한 품목에 묶이지 않습니다.**

- **품목마다 뱅크가 따로입니다.** 라인·품목을 키로 뱅크를 찾고, 없으면
  "배포된 모델이 없다"로 멈춥니다. 품목이 늘어도 코드가 바뀌지 않습니다.
- **조회 계층이 인터페이스로 분리돼 있습니다.** 함수 8개만 구현하면 사내
  MES·이미지 저장소에 연결됩니다. 임시 대체물을 빼고 끼우는 자리가 한 곳
  (`run_pipeline(lookup=...)`)입니다.
- **야간 누적분을 예약 실행으로 처리합니다.** 사람이 보고하지 않아도
  지정 시각에 미검출을 찾아 진단까지 돌립니다.
- **PatchCore 구조에 묶이지만 그것이 현장 표준입니다.** 정상 이미지만으로
  세우고 라벨이 필요 없어 도입 장벽이 낮은 방식입니다.

## 8. 의도적으로 하지 않는 것

**무인 배포를 만들지 않습니다.** 릴리즈 에이전트는 배포 패키지와 승인 요청
문서까지만 만듭니다. 실제 장비 반영을 자동화하는 코드는 저장소에 없습니다.
품질 검사 설비의 특성상 의도적으로 배제한 설계이며, 이 경계 자체가 제안의
설득 근거입니다.
